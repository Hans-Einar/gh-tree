## Contract and mechanism conclusion

Application--Persistence 1.0.0 assigns native preparation, object verification and recovery evidence to Persistence. Its recovery section expressly distinguishes stable persisted RecoveryID, artifact observation SourceVersion, and original/proposed whole-document StorageVersion. Neither that contract nor Storage--001 fixes creation time as the artifact incarnation algorithm. BoundaryTypes B3 separately defines DirectoryIdentity. A private Windows artifact profile containing full FileIdInfo volume/128-bit FileID and the complete returned 64-byte FILE_OBJECTID_BUFFER therefore fits the existing opaque observation identity. It changes no port, document schema, caller authority, commit effect or recovery policy.

This conclusion does **not** permit changing directory/root/Expected-anchor identity, permanent-lock identity, StorageVersion equality, native class65 publication/class11 retention, no-follow acquisition, security/byte comparison, or Windows durability/outcome semantics. Equal tuple evidence identifies the retained object under the supported native profile; it does not prove that an earlier operation published it. Restart still cannot infer historical causality, retry, replay or delete from matching bytes or IDs.

Microsoft's [rename algorithm](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/87f86c9b-6c2a-4803-84b7-131a74a434fa) explicitly permits cached creation-time transfer. When a rename source already has an ObjectID, the relevant cached-ID branch reports a collision instead of assigning that cached ID to the source. This supports the prepublication-ID strategy, with actual class65 execution below supplying implementation evidence. ObjectID alone remains insufficient: the native negative control reproduced ID transfer to a different FileID.

[CREATE_OR_GET](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_create_or_get_object_id) creates only when absent; [GET](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_get_object_id) never creates one. The [FSA creation algorithm](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/4f329bbc-eacf-4839-9e46-dd7780759132) describes optional support, failure cases, native ID generation and returned length. These are reasons to fail precisely when unavailable, not choose an alternate primitive. [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) specifies comparing the full file identifier and volume. The [ObjectID buffer](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-file_objectid_buffer) has a 16-byte identifier and 48 bytes of associated information; preserve all 64 bytes as opaque evidence, without interpreting the extra bytes as a second authority or requiring documented optional birth fields to be nonzero.

## Required adoption scope

1. Issue CREATE_OR_GET only on a successfully and exclusively FILE_CREATE-created owned regular artifact: manifest, raw backup and payload. Do this before its first journal/data flush and before publication. A hardlink/reopened name is not a newly created file object and must use GET only. User originals, directories and locks never receive an ID merely for proof. Keep native handles request-owned; initialization failure must close them, preserve any actual abandoned artifact fact and prevent publication.

2. Capture a tagged private artifact profile and compare that recorded profile thereafter. New ObjectID profiles require exact volume, all 16 FileID bytes and all 64 ObjectID-buffer bytes. Preserve `winObserve`'s native FileIdInfo layout, nonzero FileID and reparse checks. Require successful native output length exactly64 and nonzero first16 ObjectID bytes. Truncated/zero/malformed output is failure. Do not replace `winObservation.sameObject` or its birth check globally to fix artifact recovery.

3. Every later validation is GET-only. A recorded ObjectID profile must refuse missing or changed ID, FileID or volume; it must never fall back to birth on any GET failure. When initially observing an untouched user original that has no ID, only the exact local native GET error `windows.ERROR_FILE_NOT_FOUND` may select the existing strict birth profile. Permission, sharing, unsupported, invalid-handle/buffer and other errors remain errors. This exception concerns GET on an already acquired regular handle; it does not prove pathname/document absence. Microsoft [FSCC's reply contract](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/09a79cae-b2d4-4e95-8bf7-c6526a88078f) likewise separates absent ID, invalid request and unsupported filesystem. No localized-text or broad `os.IsNotExist` classifier is sufficient.

4. Preserve old manifests exactly. Current `manifest.go` stores artifact identity in private `diskIdentity`; both ordinary and journal decoders enforce exact shapes, and `manifestSuccessor` prevents changing an already recorded identity. A reader must choose the comparison from each recorded profile, including manifest self-identity, rather than always recomputing today's preferred profile. Existing birth manifests still require their exact birth tuple even if the file now has an ObjectID. A mismatching old record remains a mismatch. Do not rewrite frames, recalculate historical IDs/observations, upgrade identities, normalize times or synthesize postpublication repair. Keep existing serialized shapes/hashes readable, or explicitly version a private reader without altering old evidence; an unconditional extra JSON field can break the current canonical-shape checks.

5. Preserve the complete request chain: capture the identity/profile before it is relied upon, persist it before reporting recovery, and revalidate retained/publisher/original entries against that evidence. Do not let final checks silently select a different profile or merely compare two freshly changed observations. Preserve per-artifact RecoveryIDs, manifest subject/parent/Expected bindings, independent byte/security checks, immutable raw backup and late-write retained-original/payload semantics. No SET/DELETE/SET_EXTENDED object-ID calls, timestamp mutation, system-setting change, security-profile waiver or publisher fallback belongs in this adoption.

The existing `nativeCreateFileMetadata` FILE_CREATE path provides a bounded initialization location; `nativeArtifactIdentity`, `observeManifest`, `verifyCurrent` and `verifyNativeEntry` require profile-aware handling. These are private Persistence changes. A proposal that instead changes a shared directory profile, public version semantics, selected publisher or acceptance guarantee requires separate BC-CHANGE review.
