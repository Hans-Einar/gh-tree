## Purpose

Define the desired target logical architecture before Broad Code Review #21. This document is a target-design hypothesis, not an exhaustive review of current code.

The current repository was sampled at package level and through representative files only. That was sufficient to see the product responsibilities that the target architecture must support: Git/GitHub navigation, worktree deployment, local/remote branch state, stash, launch discovery, process/PTY sessions, persistence, application orchestration and Bubble Tea presentation.

The Broad Review must later challenge this target against full code evidence and may recommend revisions.

## Product capabilities considered

The architecture must support these vertical Slices without allowing one implementation file to become a cross-layer grab-bag:

- repository/PR/branch discovery and navigation;
- Active worktree selection and persistent user-owned test/deployment target;
- safe branch/PR/commit deployment into Active worktree;
- dirty-worktree protection, stash creation/list/apply/pop/drop;
- local branch versus upstream/remote state, ahead/behind/diverged and push/pull decisions;
- commit history and diff/graph inspection;
- launch-point discovery from project manifests/configuration;
- launch execution, stop/restart and deterministic process-tree lifecycle;
- interactive PTY/ConPTY terminal sessions;
- console tabs and session activity state;
- TUI focus/navigation/modal behavior;
- TUI rendering, colors, help/footer and activity animation;
- local persisted gh-tree state and user/repository configuration;
- cross-platform Windows/Linux/macOS behavior and release packaging.

## Proposed target layer map

| Layer | Responsibility | Must not own | Suggested physical package |
|---|---|---|---|
| **Domain** | Pure semantic types, invariants and value objects: Repository, PR, Branch, Commit, Worktree, Stash, LaunchPoint, Session identity/state, local/upstream relationship, safe-operation classifications | Git commands, GitHub API, process spawning, Bubble Tea, filesystem persistence, UI focus | `internal/domain/` |
| **Application** | Vertical use-case orchestration; commands/queries/events; coordinates ports; owns operation sequencing and user-intent-safe async semantics | Concrete Git/GitHub/process implementations, terminal rendering, Lip Gloss/Bubble Tea state, OS process APIs | `internal/application/` |
| **Git** | Local repository adapter: refs, commits, worktrees, stash, diff/graph source, checkout/deploy, fetch/pull/push primitives; implements Application ports | UI state, launch sessions, GitHub REST, product workflow decisions such as focus or modal behavior | `internal/git/` |
| **GitHub** | Remote GitHub adapter: PR/branch metadata and GitHub mutations required by accepted use cases | Local Git mutation, worktree lifecycle, UI focus, process runtime | `internal/github/` |
| **Runtime** | Process/session lifecycle, process groups/job objects, PTY/ConPTY, terminal I/O, stop/restart/cleanup, foreground/activity signals | Launch discovery, Git operations, TUI focus/rendering, repository state policy | `internal/runtime/` |
| **Launch Discovery** | Discover and normalize launch points from npm/pnpm/yarn/Make/config; produce domain LaunchPoint definitions | Starting/stopping processes, console state, Bubble Tea rendering | `internal/launchdiscovery/` |
| **Persistence** | Local gh-tree state/configuration and durable preferences; repository/user scoped persistence | Git domain mutation, UI orchestration, process lifecycle | `internal/persistence/` |
| **TUI State** | Pure interaction/controller state: active pane/subpane, selection, modal state, key intent, local view projections, focus authority; translates user actions to Application commands and consumes results/events | Git commands, process spawning, GitHub API, Lip Gloss styling/layout, authoritative process/Git state | `internal/tuistate/` |
| **TUI View** | Rendering only: layout, colors, focus headers, tables/lists, help rows, modal overlays, activity animation from supplied view model | Business decisions, Git/process operations, async authority, changing user focus | `internal/tuiview/` |
| **Composition** | Bootstrap/wiring of concrete adapters to Application and TUI; CLI flags/version/release entrypoint | Business logic or layer-local implementation | `cmd/gh-tree/` plus, if needed, a small `internal/composition/` |

### Why these layers

The split deliberately separates three things that are currently easy to conflate:

1. **authoritative product state and semantics** (`Domain` + adapter-owned external state),
2. **vertical orchestration** (`Application`), and
3. **presentation interaction/rendering** (`TUI State` + `TUI View`).

It also separates **launch discovery** from **runtime execution**. A script definition is repository/project metadata; a running process/PTY is an OS resource with lifecycle semantics. They need different ownership.

## Target physical package/directory map

```text
cmd/
  gh-tree/                 # Composition root / CLI bootstrap

internal/
  domain/                  # Pure types + invariants
  application/
    api/                   # Commands, queries, result/event DTOs exposed upward
    ports/                 # Interfaces required from infrastructure layers
    usecases/              # Vertical orchestration
  git/                     # Local Git/worktree/stash/diff/graph adapter
  github/                  # GitHub remote adapter
  runtime/                 # Process groups, PTY/ConPTY, sessions, terminal I/O
  launchdiscovery/         # Manifest/config discovery only
  persistence/             # config + persisted gh-tree state
  tuistate/                # interaction state machine/controller
  tuiview/                 # rendering only
  composition/             # optional wiring helpers; Master-owned
  version/                 # tiny build/version support may remain separate
```

The final Broad Review/Refactor Design may choose subpackages inside a layer, but production files must have one unambiguous horizontal owner.

Existing feature-oriented packages such as graph/diff may become subpackages of `git` if they are purely local Git read models, or Application read-model helpers if evidence shows they contain orchestration. Broad Review #21 must decide from code evidence.

## Dependency direction

Desired dependency rule:

```text
                     ┌──────────────┐
                     │ Composition  │
                     └──────┬───────┘
                            │ wires concrete implementations
          ┌─────────────────┼───────────────────┐
          ▼                 ▼                   ▼
      TUI State        Application         infrastructure adapters
          │                 │              Git / GitHub / Runtime /
          │                 │              LaunchDiscovery / Persistence
          ▼                 ▼                   │
       TUI View           Domain ◄───────────────┘
```

More precisely:

- `TUI View` depends only on presentation view-model types, ideally owned by `TUI State` or a presentation DTO package.
- `TUI State` depends on `Application/api` and selected stable Domain/read-model types.
- `Application` depends on Domain and interfaces in `Application/ports`.
- `Git`, `GitHub`, `Runtime`, `LaunchDiscovery`, and `Persistence` implement Application ports and may depend on Domain plus those port interfaces.
- Concrete adapters do not import each other.
- Application does not import concrete adapters.
- Domain imports no other product layer.
- Composition is the only normal place allowed to import all concrete layers.

This avoids the common failure mode where a central service imports every concrete package and therefore becomes both orchestration and infrastructure ownership.

## State authority map

| State / concept | Authoritative layer | Consumers | Mutation rule |
|---|---|---|---|
| Branch/commit semantic identity | Domain, populated by Git/GitHub adapters | Application/TUI | Adapters report facts; Application reconciles local/upstream view |
| Local HEAD/ref/worktree/stash state | Git | Application/TUI projection | Only Git adapter mutates repository state under Application command |
| GitHub PR/remote branch facts | GitHub | Application/TUI projection | GitHub adapter owns remote API facts; no TUI direct mutation |
| Local-vs-upstream relation (`ahead/behind/diverged`) | Application read model derived from Git facts | TUI | One canonical calculation/result; TUI does not infer from unrelated SHA fields |
| Active worktree preference | Persistence + Application session context | TUI/Application | User intent changes through Application command; persisted atomically |
| Running process/PTY lifecycle | Runtime | Application/TUI projection | Runtime owns PID/process-group/job/PTY truth |
| Console tab selection/focus | TUI State | TUI View | Only direct user-intent state transitions may change focus |
| Launch-point definitions | Launch Discovery | Application/TUI | Discovery produces immutable normalized definitions |
| Operation progress (`starting/running/stopping`) | Application operation + Runtime facts | TUI | Background completion updates operation/session result, never unrelated focus |
| Render colors/layout/animation frame | TUI View | terminal only | Presentation-only; no product-state authority |

### User intent versus async completion

A core architectural invariant should be frozen later in a BC:

> Background completion may update the result/state of the operation it belongs to, but it must not overwrite newer independent user intent such as active pane/focus unless that focus transition is an explicit part of the still-current user command and has not been superseded.

TUI focus therefore belongs exclusively to `TUI State`, not to Runtime/Application completion handlers.

## Lifecycle/resource authority

| Resource | Owner layer | Start | Stop/cancel | Cleanup invariant |
|---|---|---|---|---|
| non-interactive launch process tree | Runtime | Application requests Runtime session start from LaunchPoint | Runtime terminates process group/job tree with bounded graceful->force escalation | no child process survives an accepted Stop/StopAll/gh-tree exit contract |
| PTY/ConPTY terminal | Runtime | Application requests terminal session with worktree cwd + shell selection | Ctrl+C may signal foreground job; explicit close/Stop terminates owned terminal resource | descriptors/handles/readers/goroutines close deterministically |
| operation/task lifecycle | Application | user command | cancellation token/command | one terminal result event per operation; stale result cannot mutate unrelated state |
| Git mutation | Git | Application command | command-specific cancellation/timeout | no silent destructive cleanup; dirty safeguards enforced |
| persisted config/state | Persistence | Application request | transaction/atomic write where relevant | no partial state or hidden chat-only configuration |

## Vertical Slice orchestration

Vertical Slices should be implemented as Application use cases, not as files spread vertically through every layer.

Example: **Deploy selected commit into Active worktree**

```text
TUI State
  -> Application DeploySelection command
      -> Git query target status
      -> if dirty: return RequiresStash confirmation result
TUI State shows modal
  -> Application ConfirmDeploy{stash=true}
      -> Git create stash
      -> Git checkout detached target
      -> Persistence keep Active worktree preference
      -> Application returns DeployCompleted read model
TUI State updates selection/status projection
TUI View renders it
```

No renderer or Bubble Tea message handler should call Git directly. No Git adapter should decide pane focus.

Example: **Run launch point**

```text
TUI State -> Application StartLaunch
Application -> Runtime StartSession(LaunchPoint command/cwd)
Runtime -> session facts/events
Application -> normalized SessionStarted/SessionExited
TUI State updates console projection
TUI View renders
```

Focus behavior remains a TUI State decision. Runtime/Application events do not forcibly pull focus back after the user has moved elsewhere.

## Candidate Layer Boundary Contracts

The Pre-study proposes these BCs for Broad Review to validate or revise:

1. `BC--TUIState--TUIView.md`
   - immutable view model, focus/highlight semantics, activity rendering, no business callbacks in view.
2. `BC--TUIState--Application.md`
   - user commands, async result/event delivery, focus/user-intent ordering rule, modal confirmation protocol.
3. `BC--Application--Git.md`
   - Git queries/mutations, safe dirty-worktree/deploy/stash semantics, local/upstream state primitives.
4. `BC--Application--GitHub.md`
   - PR/remote branch facts and allowed remote mutations.
5. `BC--Application--Runtime.md`
   - process/PTY session start/stop/restart, process-tree guarantees, output/activity/events, cancellation.
6. `BC--Application--LaunchDiscovery.md`
   - normalized LaunchPoint discovery and cwd/project-root semantics.
7. `BC--Application--Persistence.md`
   - active worktree, repository/user settings and atomic persistence semantics.
8. `BC--Application--Domain.md` is likely **not** needed as a traditional adapter BC if Domain is a pure lower layer; its invariants should instead be documented in Domain design/API. Broad Review should confirm.
9. `BC--Composition--Layers.md` may be a lightweight wiring/dependency policy rather than runtime API contract; CI dependency rules may be more useful than a full BC.

BCs are candidates only. None are frozen by this Pre-study.

## Parallel-development ownership

If the target layout is accepted, it supports clean parallel worktrees:

```text
codereview-#21/layer-domain
codereview-#21/layer-application
codereview-#21/layer-git
codereview-#21/layer-github
codereview-#21/layer-runtime
codereview-#21/layer-launchdiscovery
codereview-#21/layer-persistence
codereview-#21/layer-tuistate
codereview-#21/layer-tuiview
```

Workers own only their layer directories and layer-local tests/docs.

Master/Integrator owns:

- `cmd/gh-tree/` composition changes;
- optional `internal/composition/`;
- `go.mod`/`go.sum` coordination when multiple layers need dependencies;
- frozen BC files;
- CI dependency-rule configuration;
- serial integration into `codereview-#21/refactor`.

A migration phase may temporarily require moving files between old and new folders. To avoid merge conflicts, Refactor Design should assign each physical move to exactly one layer worker or to Master; two workers must never independently edit/move the same legacy file.

## Architecture questions for Broad Review #21

Broad Review must challenge at minimum:

1. Is `Domain` sufficiently meaningful to justify a separate pure package, and which current types can move there without adapter leakage?
2. Which current `worktree`, `graph`, and `diff` code is pure Git adapter logic versus Application orchestration/read-model logic?
3. Does current `app.Service` contain orchestration worth preserving, or is it mainly a concrete-adapter facade that should be replaced by port-based use cases?
4. How many current TUI files mix controller state, async orchestration and rendering, and what migration boundaries minimize risk?
5. Can `TUI State` be made deterministic/pure enough to unit-test user-intent ordering independently from Bubble Tea commands?
6. Which launch package files are discovery versus runtime/session lifecycle, and what exact types should cross `Application--Runtime`?
7. What platform abstraction is needed for Windows Job Objects/process groups and Unix process groups/PTY without leaking OS details upward?
8. Should interactive-shell foreground activity be a Runtime fact, an Application heuristic, or an optional capability? Define reliable semantics before promising `idle/running` distinctions.
9. How should local branch, upstream ref and GitHub branch tips be reconciled so `ahead/behind/diverged/unpushed` has one canonical model?
10. Which current persisted state belongs to Persistence versus TUI-only ephemeral state?
11. Can graph/diff remain separate implementation packages under `git`, or should they be read-side services with their own explicit port?
12. What migration order allows current v0.3.x behavior to remain testable while removing the stacked `V310..V314` model wrappers?
13. Which layer boundaries need compile-time import enforcement in CI?
14. Which shared legacy files are unavoidable during migration and therefore must be Master-owned until split?

## Preliminary release-line impact

**Recommendation: plan the refactor on a new `v0.4` architecture line, while keeping `v0.3.x` available for bounded fixes.**

Rationale:

- the target introduces explicit port-based Application orchestration;
- TUI controller/state and rendering are intentionally split;
- launch discovery and process/PTY runtime are intentionally split;
- local Git semantics are separated from product workflow decisions;
- many legacy files are expected to move/split physically;
- parallel layer implementation and stabilization are likely to span multiple Slices.

This is a preliminary architecture recommendation. Broad Review #21 and focused Layer Reviews must confirm the migration size before Steering freezes the release-line decision.
