## Review purpose

This review maps the complete current production architecture at system level against APS--001 and identifies where horizontal ownership is absent, duplicated or physically mixed. It intentionally does not freeze the final refactor design, freeze Boundary Contracts, perform line-by-line review of one package, or implement fixes.

The product baseline is exactly `f626077ca0e59fbe9ede7ba1116982bb94b2eb6b`. Governance and architecture-documentation commits after that SHA were treated only as process/design authority.

The APS layer set remains broadly valid after challenge against code evidence. The largest corrections are not new layers, but stricter boundaries: current `graph` is not a pure Git adapter because it joins Git facts with GitHub PR/worktree annotations; current `launch` contains both discovery and runtime/session implementation and must be physically split; and current `internal/tui` contains substantial Application and Runtime interaction logic in addition to presentation state/view.

The key invariant for later BCs is confirmed: **background completions may update only the operation/session result they belong to. They must not mutate focus/selection/modal intent unless the completion carries a still-current explicit user-intent token and that transition is part of that command contract.**

## Lifecycle / concurrency findings

1. Runtime must own a logical session resource, not merely a PID. The resource includes the complete process tree, PTY/ConPTY handles, goroutines/readers, output buffers and exit/cancellation completion.
2. `Stop`, `Restart`, `StopAll`, program exit and failed-start cleanup require one idempotent lifecycle contract with bounded graceful->force escalation and a terminal completion event.
3. Windows needs an implementation capable of terminating owned descendants (normally Job Object semantics or an equivalently strong abstraction); Unix needs process-group semantics rather than direct-child-only `Process.Kill`.
4. Terminal sessions and non-interactive launch sessions should implement the same Runtime port at the Application boundary while retaining capability differences (write/resize/foreground-signal).
5. Application async operations need stable operation IDs/generations and exactly-one terminal result; TUI should discard stale projections without special-casing message types ad hoc.
6. Runtime session existence, process state and foreground/user activity are separate concepts. An interactive shell can be alive but idle. The Runtime review must define what can be observed reliably before exposing an `active` signal.
7. Direct `context.Background()` use from TUI commands prevents cancellation from following user intent/application operation lifetime. Cancellation semantics belong in the Application command/Runtime port contract.

## Required Application ports/interfaces

Names are preliminary; focused reviews/refactor design may rename them.

- `GitRepositoryPort`: repository/ref/commit/worktree/status/stash/diff/graph primitives and safe local mutations.
- `GitHubPort`: PR/branch remote facts and approved remote mutations.
- `RuntimePort`: start/stop/restart/stop-all/snapshot/events for launch and terminal sessions, with capability flags for terminal I/O/resize/interrupt.
- `LaunchDiscoveryPort`: discover normalized launch points for a project/worktree.
- `PersistencePort`: load/save repository-scoped navigation/active-worktree/settings state with explicit error and atomicity semantics.
- Optional `Clock`/`OperationID` source only if deterministic async testing needs it; do not introduce unless Layer Review evidence justifies it.

Application should expose use-case APIs/results upward, for example load navigator, deploy selection, activate worktree, stash operations, fetch/pull/push, start/restart/stop console, discover launches, load graph/diff. These APIs should return Domain/Application DTOs, never concrete adapter structs.

## Boundary-contract candidates / changes to APS--001

APS--001's candidate BC set is retained with these revisions/additions:

1. **`BC--TUIState--Application` — required, expanded.** Must define command IDs/generations, cancellation/supersession, exactly-one completion, stale-result handling, modal confirmation protocol, and explicit prohibition on background focus mutation.
2. **`BC--Application--Runtime` — required, stronger than APS text.** Must define logical session ownership, descendant process-tree guarantee, Stop/Restart/StopAll idempotence, graceful/force timing semantics, PTY resource cleanup, event ordering and activity capability semantics.
3. **`BC--Application--Git` — required.** Must distinguish local ref, configured upstream ref, remote-tracking observation and fetched freshness. Safe deploy/stash dirty-worktree rules belong here at the primitive boundary while use-case sequencing remains Application.
4. **`BC--Application--GitHub` — required.** Must return remote facts in adapter-neutral DTOs and state freshness/error semantics.
5. **`BC--Application--LaunchDiscovery` — required.** Must pass normalized immutable LaunchPoint/Invocation definitions without runtime session state.
6. **`BC--Application--Persistence` — required.** Must state repository keying, atomic write expectations, error handling and which changes are durable user intent.
7. **`BC--TUIState--TUIView` — required.** View receives immutable projection; cannot mutate focus, issue Git/runtime calls or own authoritative animation/activity policy beyond rendering supplied state.
8. **Domain contract remains design/API, not a traditional adapter BC.** This agrees with APS--001.
9. **Composition dependency policy should be CI-enforced rather than a large runtime BC.** A short wiring policy document may be sufficient.
10. **New candidate: Application read-model reconciliation rule** should be part of `Application--Git` + `Application--GitHub` contracts or Application design, not a separate layer: one canonical branch relationship must distinguish `local`, `upstream-tracking`, and `GitHub remote` observations and their freshness.

No BC is frozen by this review.

## Physical layer-separation findings

The refactor can achieve disjoint worker ownership only **after** a designed extraction phase. The current code cannot safely be divided by simply assigning legacy folders to workers because the worst folders are themselves vertical mixtures.

Recommended migration ownership principle:

- Layer workers create/own new target folders only after Refactor Design + BC freeze.
- Every legacy source file has exactly one migration owner.
- The V310->V314 chain, `model.go`, `app.Service`, shared launch/worktree types, composition root, `go.mod/go.sum` and dependency-check CI remain Master-owned until extraction points are frozen.
- Prefer adapters moving first behind ports while preserving behavior; only then replace legacy TUI orchestration and wrappers.
- Compatibility shims, if required, are Master-owned and temporary with removal criteria in Refactor Design.

After this extraction is designed, workers **can** operate safely on disjoint physical folders. Before that point, parallel edits to current `tui`, `app`, `launch` or shared adapter DTOs would create ownership ambiguity and merge conflicts.

## Focused Layer Review plan and recommended execution order

Recommended order is risk/dependency driven rather than target-list order.

1. **Runtime Layer Review** — highest safety/lifecycle risk; define process-tree/session facts, PTY/ConPTY capabilities, Stop/Restart/StopAll and activity semantics.
2. **TUI State Layer Review** — map all V310..V314 fields/message handlers, authoritative focus/selection/modal state, async supersession and persistence callbacks.
3. **Application Layer Review** — separate real orchestration from `Service` pass-through facade; define operation model and required ports using Runtime/TUI evidence.
4. **Git Layer Review** — worktree/ref/stash/deploy/diff/graph primitives; local/upstream/freshness facts and safe mutation contracts.
5. **Domain Layer Review** — extract only semantic types proven stable by Runtime/Application/Git evidence; avoid premature DTO dumping ground.
6. **Launch Discovery Layer Review** — isolate config/npm/make/registry behavior and normalized LaunchPoint contract from runtime.
7. **Persistence Layer Review** — config/state authority, repository identity/keying, atomic writes and Application ownership of durable intent.
8. **GitHub Layer Review** — adapter-neutral remote facts, PR/branch semantics, freshness and allowed mutations.
9. **TUI View Layer Review** — rendering-only split, view model, graph UI convergence, animation supplied-state semantics.
10. **Composition Layer Review** — final wiring root, startup/exit lifecycle, prerequisites and CI import enforcement; intentionally last because it consumes all other boundaries.

Reviews 1 and 2 may run in parallel because they inspect different evidence but should both finish before Application review is accepted. Git and Launch Discovery reviews can overlap once Application port questions are recorded, but final BC design remains serial/Master-owned.

## Release-line recommendation

**Use a new `v0.4` architecture line. Keep `v0.3.x` available for bounded stabilization fixes.**

Broad Review independently confirms APS--001's preliminary recommendation.

Reasons:

- Application API changes from concrete-adapter facade to explicit ports/use cases.
- Runtime lifecycle semantics must materially change to own process trees and unified launch/terminal sessions.
- TUI controller/state and rendering must be physically separated while eliminating a five-generation wrapper chain.
- Git local/upstream/GitHub branch semantics need a canonical model.
- Several shared DTOs move ownership across packages.
- Migration needs Master-owned compatibility/extraction points before parallel folder ownership is safe.

Trying to land this as a sequence of ordinary v0.3 patch refactors would make architectural intermediate states user-facing and increase merge/regression risk. The current v0.3.x line should remain the patch/stability line while v0.4 carries the architecture program.
