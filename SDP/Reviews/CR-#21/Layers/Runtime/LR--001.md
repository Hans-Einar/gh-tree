## Review purpose

This review inspects only the Runtime horizontal responsibility deeply enough to define authoritative lifecycle, process-tree, PTY/ConPTY, event, capability and cancellation requirements for the later Refactor Design and `BC--Application--Runtime.md`.

It does not implement fixes, freeze a Layer Boundary Contract, design the whole refactor, or perform a full TUI/Application review. TUI and Application code are inspected only where they expose or consume Runtime behavior.

Governance/review/documentation commits after the product SHA are treated as process/design authority only and not as product changes.

## Layer responsibility

### Runtime must authoritatively own

Runtime must own the complete lifetime of every OS-backed execution session created on behalf of gh-tree. The authoritative resource is not a PID. It is a logical **Runtime Session Resource** containing, as applicable:

- stable session identity;
- session kind/capabilities;
- command/process specification received from Application;
- direct child process handle;
- complete owned descendant process tree containment mechanism;
- Unix process-group/session-group identity or Windows Job Object/equivalent ownership handle;
- PTY/ConPTY object and associated descriptors/handles;
- stdin/write endpoint when supported;
- resize endpoint when supported;
- signal/interrupt endpoint when supported;
- output capture/buffer/stream resources;
- wait/completion synchronization;
- reader/wait goroutines and their termination;
- lifecycle state and exit result;
- stop/cancel intent state distinct from observed process exit;
- cleanup state proving owned resources are released.

Runtime is authoritative for facts it can directly observe about those resources: session creation, process started, process tree still owned/alive, terminal open/closed, exit status, output observed, and cleanup completion.

### Runtime must not own

Runtime must not own:

- discovery of npm/Make/config launch points;
- Git/worktree validation or mutation;
- pane/console selection or focus;
- modal state;
- UI activity animation policy;
- interpretation of a shell being `idle` versus a command being `working` unless a platform-specific observation has an explicit reliable contract;
- vertical user workflow sequencing beyond lifecycle operations on one or all Runtime sessions;
- persistence;
- Application operation supersession/user-intent policy.

## Challenge of Broad Review findings

### BR21-H01 — confirmed and strengthened

The Broad Review correctly found direct-child-only stop behavior. Deeper Runtime inspection shows an additional state-authority defect: both launch and terminal code can publish `stopped` before termination is proven.

`launch.SessionManager.StopSession` sets `s.state = StateStopped` before signaling/killing the process. If kill fails, the method returns an error but the snapshot can still claim `stopped` while the process or descendants remain alive.

`terminal.Manager.Stop` similarly sets `stopped=true` and `StateStopped`, closes the PTY, ignores PTY-close errors, calls `proc.Kill()` while ignoring the kill error, and returns without waiting for process termination. Thus `StateStopped` currently means stop was requested, not that the owned resource is quiescent.

The later contract must separate **stop requested / stopping** from **confirmed stopped/terminated**.

### BR21-M01 — confirmed, with narrower Runtime promise

`V314Model.realActivity314` treats non-terminal `running/starting` sessions as activity and excludes provider `terminal`. Runtime review confirms the TUI cannot safely infer `working` from process existence or provider name.

A portable Runtime can reliably expose lifecycle state, terminal-alive state, output observations (for example monotonic output sequence / last-output timestamp), and possibly explicit platform capabilities. It cannot generally distinguish an idle shell from a foreground command solely from generic PTY/process state. No BC should promise `working/idle` unless implementation provides a defined, tested observation mechanism.

### BR21-M05 — confirmed and strengthened

Composition defers `service.StopAllConsoles()`, but `Service` coordinates two independent managers. Cleanup errors are ignored by the deferred caller. Neither manager provides a proof that all descendants, PTY handles, goroutines and waiters are quiescent before process exit returns.

Application exit must invoke one Runtime shutdown operation and receive a bounded aggregate result. A successful shutdown result must mean every owned session is terminal and resources are cleaned. Failure must identify residual sessions/resources.

### BR21-M06 — confirmed

`internal/launch` mixes discovery (`Candidate`, providers, Registry) with execution (`SessionManager`, process state/snapshot). `internal/terminal` then imports launch-owned execution DTOs. Runtime therefore depends on the Launch Discovery package for its public state vocabulary. This dependency is architecturally reversed and must disappear.

## Authoritative state model

Runtime must model distinct facts rather than overloading one `ProcessState` value.

Minimum lifecycle phases/observations required conceptually:

| Concept | Meaning | Authority |
|---|---|---|
| Session exists | Registry has a logical session identity/history record | Runtime |
| Starting | Resource acquisition/process start is in progress | Runtime |
| Running | Root process/session resource is started and not yet observed terminal | Runtime |
| Stopping | Stop accepted; graceful/force cleanup is in progress | Runtime |
| Exited | Process tree terminated naturally; exit result known as applicable | Runtime |
| Failed start | Session did not establish successfully; partial resources cleaned before terminal result | Runtime |
| Failed runtime | Session terminated abnormally / lifecycle operation failed with explicit residual-resource status | Runtime |
| Stopped | Stop completed and Runtime has proven its owned process tree/session is terminal and cleanup requirements are satisfied | Runtime |
| Terminal alive | PTY/ConPTY resource remains usable/open | Runtime |
| Output observed | Runtime has received bytes/chunks/lines; sequence/timestamp can be reported | Runtime |
| Command actively working | Not generally inferable from generic process/PTY existence | Not promised unless explicit platform capability exists |
| Shell idle | Not generally inferable portably | Not promised by default |

A `stopped` state must never be a synonym for `stop requested`.

### State transitions

Expected shape:

```text
created/starting
  -> running
  -> exited | failed-runtime
  -> stopping -> stopped | stop-failed-with-residual-state

created/starting
  -> failed-start (only after partial-resource cleanup is complete)
```

Exact enum names belong to Refactor Design, but semantic separation is mandatory.

## Logical Runtime session and capability model

Launch jobs and interactive terminals should implement **one Runtime session abstraction** because Application needs one identity/lifecycle/event model. They should not pretend to have identical operations.

The session contract should expose explicit capabilities, for example conceptually:

| Capability | Launch job | Interactive PTY/ConPTY terminal |
|---|---:|---:|
| output | yes | yes |
| stop | yes | yes |
| restart | yes | yes |
| stdin/write | optional/no by default | yes |
| resize | no | yes |
| interrupt/Ctrl+C | platform/contract dependent | yes as terminal input or explicit foreground interrupt capability |
| terminal semantics | no | yes |

Unsupported capabilities must return a typed/explicit unsupported result, not be inferred by provider string.

Session kind (`launch`, `terminal`, future kinds) may exist as descriptive metadata, but routing must use opaque SessionID and capabilities through one registry.

## Process-tree contract requirements

### Windows

The current direct `Process.Kill()` behavior is insufficient.

Runtime must establish a strong descendant-ownership mechanism at process creation. The preferred Windows design candidate is a **Job Object** configured so the Runtime can terminate the complete owned process tree and so owned descendants do not silently escape normal cleanup. An equivalent mechanism is acceptable only if it provides the same tested invariant.

Required Windows invariant:

> After Runtime reports successful Stop/StopAll/shutdown for a session, no process that belongs to that Runtime-owned session tree remains alive solely because it was a descendant of the launched root process.

The implementation must account for creation/assignment ordering so a child cannot spawn descendants before containment is established, as far as supported by the chosen Windows mechanism. The exact suspended-create/assignment strategy is a Refactor Design/platform implementation question.

### Unix-like systems

Runtime should create the launched root in a dedicated process group (or session group where PTY semantics require it) and signal the owned group rather than only the root PID.

Expected policy:

1. establish process-group/session ownership at start;
2. graceful stop signals the owned group with the contract-selected interrupt/termination signal;
3. wait a bounded grace interval;
4. force kill the owned group if still alive;
5. reap/wait the root process;
6. prove owned group is quiescent to the extent the platform contract supports;
7. close PTY/descriptors and join Runtime goroutines;
8. emit terminal completion exactly once.

PTY session-group/foreground-process-group semantics require platform-specific care and must be covered by terminal integration tests.

## Lifecycle ownership model

### Start

A successful Start must mean:

- a unique SessionID has been allocated;
- required containment (process group/job) is established;
- required PTY/ConPTY is established for terminal sessions;
- root process is started;
- Runtime has installed wait/output ownership;
- a session-started/result event is generated under the Application operation that requested it.

Start must not return success while tree containment is still optional/unowned.

### Failed Start

If any step fails after resource allocation:

- Runtime must synchronously or deterministically complete rollback of partial OS resources;
- no root/descendant process may remain;
- PTY/job/process handles must be closed;
- goroutines started during partial setup must terminate;
- one terminal failed-start result/event is produced;
- the contract must define whether a failed session record remains queryable for diagnostics. If retained, its ID remains unique and terminal.

### Stop

Stop is idempotent by SessionID.

- stopping a running/starting session initiates bounded graceful->force cleanup;
- stopping a session already terminal returns success/idempotent terminal result unless prior cleanup remains unresolved;
- successful return means confirmed terminal + required resource cleanup, not merely signal sent;
- failure returns residual-state information sufficient for Application/diagnostics to know cleanup is incomplete.

### Restart

Restart is an Application-visible lifecycle operation implemented using Runtime guarantees.

Required semantics:

- old session must reach confirmed terminal cleanup before replacement is considered started;
- replacement receives a new SessionID; identity must not be silently reused;
- result identifies old and replacement session IDs and the operation ID;
- if stop fails, replacement is not started unless a later design explicitly defines a safe alternative;
- if replacement start fails, old session remains terminal and result clearly reports restart failure; it must not fabricate continuity.

### StopAll

StopAll/Shutdown must:

- snapshot the set of owned live/starting/stopping sessions under registry synchronization;
- attempt cleanup for every session even if one fails;
- be idempotent;
- return an aggregate result describing failures/residual resources;
- not report success until all included sessions are terminal and cleaned;
- define behavior for sessions concurrently being started. The preferred contract is shutdown gating: once shutdown begins, no new starts are accepted.

### Application exit

Composition is the lifecycle root but Runtime is the resource owner.

`cmd/gh-tree/main.go` should eventually call one Runtime shutdown/close operation through Application/composition wiring. The exit path must not silently discard a cleanup failure. Exact UX/reporting is an Application/Composition concern, but successful program teardown must invoke the Runtime shutdown contract.

## Graceful -> forced termination policy

The BC should define semantics, while exact durations remain configurable/design-owned.

Required phases:

1. mark stopping / reject conflicting lifecycle mutation;
2. deliver graceful interrupt/termination using the owned tree/group mechanism when supported;
3. wait bounded grace period for terminal completion;
4. escalate to force termination of the entire owned tree/group;
5. wait bounded force-completion period;
6. reap process state;
7. close terminal/output resources;
8. join/terminate Runtime goroutines;
9. emit terminal event exactly once.

A force-termination timeout must return an explicit residual-resource error; Runtime must not relabel the session `stopped` if OS ownership remains unresolved.

## Idempotency requirements

- `Stop(sessionID)` is idempotent.
- `Shutdown/StopAll()` is idempotent.
- repeated observation/snapshot is side-effect free.
- terminal cleanup/Close is safe to repeat.
- exactly one terminal lifecycle event is emitted per session generation.
- Restart itself must be protected against duplicate concurrent execution for the same source session/operation ID.
- stale duplicated Application requests must be distinguishable with operation IDs rather than accidentally producing multiple replacements.

## Completion / event semantics

Runtime should expose lifecycle/output events or an equivalent subscription mechanism to Application; TUI-specific message types do not belong in Runtime.

At minimum events/results need:

- SessionID;
- operation correlation ID where the event is a response to Start/Stop/Restart;
- lifecycle generation/replacement relationship for Restart;
- monotonic ordering information per session (sequence number or equivalent);
- lifecycle phase/result;
- exit status / signal / forced-stop cause where available;
- error/residual-resource status;
- capability metadata on session establishment;
- output sequence/chunk metadata separately from lifecycle state.

Application, not Runtime, decides whether a late completion is stale relative to newer user intent.

## Session ID / operation ID requirements

### Session ID

The current numeric-range partition is rejected.

Requirements:

- allocated by one Runtime registry or otherwise guaranteed collision-free across all session kinds;
- opaque to TUI and Application business logic;
- not encode provider/kind routing assumptions;
- never reused during one gh-tree process lifetime;
- Restart creates a new SessionID.

A monotonic 64-bit ID is sufficient if allocated centrally; UUID is not required unless later design needs cross-process identity.

### Operation ID

Application should create/own operation correlation IDs for user-intent operations. Runtime must echo/carry the supplied ID in terminal results/events.

Runtime does not decide focus supersession. It guarantees correlation and exactly-once terminal operation result so Application can decide whether an event is still relevant.

## Concurrency / cancellation requirements

### Registry locking

One Runtime registry should serialize membership/identity/shutdown gating without holding the global lock across long OS waits.

Per-session synchronization should own lifecycle mutation. Concurrent Stop/Restart/write/resize requests must have defined ordering and typed outcomes.

### Goroutines

Every goroutine created for wait/output must have an owner and deterministic terminal condition.

The current terminal `readLoop` and `waitLoop` have no exposed join/completion primitive. Refactor Design must require a session-level completion/cleanup barrier.

### Output buffers

Buffers must be bounded and concurrency-safe. Retention policy should be explicit. Runtime should expose transport/output facts; presentation-specific ANSI stripping/layout should not silently become lifecycle authority.

### Cancellation

Application -> Runtime operations should accept cancellation/deadline context where meaningful.

Important distinction:

- cancellation **before Start is established** should abort setup and clean partial resources;
- cancellation **after a successful persistent session Start** should not implicitly kill the session merely because the initiating request context ends, unless the port contract explicitly says that session lifetime is context-bound;
- Stop/Restart/Shutdown contexts bound how long the caller waits, but Runtime must define what happens to cleanup if caller cancellation occurs mid-cleanup. Resource ownership cannot simply be abandoned.

The preferred invariant is that Runtime continues/owns mandatory cleanup once accepted, while returning a typed timeout/cancellation outcome to the caller if its wait budget ends.

## Activity semantics

The following concepts must remain separate:

| Observation | Can Runtime reliably expose? | Notes |
|---|---|---|
| session record exists | yes | Registry fact |
| root/session running | yes | Lifecycle fact |
| terminal PTY/ConPTY alive | yes | Resource fact |
| bytes/output recently observed | yes | Observation, not proof of computation |
| process tree has descendants | platform dependent but feasible | Diagnostic fact, not UI `working` truth |
| shell idle at prompt | not generically/portably reliable | Do not promise by default |
| foreground command actively working | not generically reliable without explicit platform instrumentation | Optional future capability only |

TUI must never infer `working` from:

- `Provider != "terminal"`;
- PID existence alone;
- terminal existence alone;
- process state `running` alone;
- absence/presence of output alone.

If UI needs an animation, Application/TUI State should define the UX meaning using explicit Runtime facts, e.g. `session running` or `output observed`, rather than call it CPU/work activity.

## Incoming boundary changes required

### From Application

Application must provide Runtime with:

- normalized executable/session start specification, not Launch Discovery `Candidate`;
- operation correlation ID;
- cancellation/deadline context;
- explicit requested session mode/capabilities where needed;
- Stop/Restart/Shutdown commands by opaque SessionID;
- no focus/view instructions.

Application must own:

- user-intent supersession;
- deciding whether a completion still affects selected/focused UI state;
- orchestration such as worktree validation before launch;
- launch discovery -> normalized start request translation.

### From Launch Discovery

Launch Discovery must stop owning Runtime DTOs. It produces normalized launch definitions/specifications only. It does not start/stop processes and must not import Runtime concrete implementation.

### From Composition

Composition constructs one Runtime implementation and wires it to Application. Platform-specific internals remain hidden beneath Runtime.

## Outgoing boundary requirements

Runtime must expose through an Application-owned port, conceptually:

- Start(startSpec, operationID, context) -> session/result;
- Stop(sessionID, operationID, context) -> terminal lifecycle result;
- Restart(sessionID, operationID, context) -> old/new session relationship result;
- Shutdown/StopAll(context) -> aggregate cleanup result;
- Snapshot/GetSession(sessionID);
- ListSessions();
- Subscribe/Events or equivalent lifecycle/output event source;
- Write(sessionID, bytes) only when capability exists;
- Resize(sessionID, cols, rows) only when capability exists;
- Interrupt(sessionID, kind) only when capability exists.

Exact Go signatures are deferred to Refactor Design/BC review.

## Proposed requirements for `BC--Application--Runtime.md`

The eventual BC must guarantee at minimum:

1. **Ownership:** Runtime exclusively owns OS session resources from accepted Start through terminal cleanup.
2. **Tree containment:** successful Start establishes process-tree ownership before reporting started.
3. **Platform guarantee:** Windows uses Job Object/equivalent strong tree ownership; Unix uses process group/session-group semantics appropriate to command/PTY sessions.
4. **Session identity:** one collision-free opaque SessionID namespace for all session kinds.
5. **Capabilities:** stdin/write, resize, interrupt, stop, restart and output are explicit capabilities; no provider-string inference.
6. **Lifecycle state:** `stopped` means confirmed termination/cleanup, never merely requested stop.
7. **Failed Start:** partial resources are cleaned before terminal failed-start result.
8. **Stop:** idempotent, bounded graceful->force escalation, whole-tree guarantee, typed residual-resource failure.
9. **Restart:** old session fully quiesces before replacement; replacement has new SessionID; result correlates both IDs.
10. **StopAll/Shutdown:** idempotent, no new starts after shutdown gate, attempts all sessions, aggregate result, success proves all owned resources cleaned.
11. **Application exit:** Composition/Application invokes Runtime shutdown; cleanup failure is observable and not silently converted to success.
12. **PTY/ConPTY:** Runtime owns PTY handles, resize/write, process wait, reader/writer goroutines and deterministic closure.
13. **Events:** lifecycle terminal result exactly once per operation/session generation; events carry SessionID + operation correlation + per-session ordering.
14. **Cancellation:** caller cancellation never silently abandons Runtime-owned resources; semantics before/after successful Start are explicit.
15. **Output:** bounded concurrency-safe output contract with explicit retention/sequence semantics.
16. **Activity:** Runtime promises only defined observable facts. `shell idle`/`actively working` are not generic lifecycle states unless an explicit tested capability is added.
17. **Errors:** distinguish unsupported capability, not-found session, already-terminal/idempotent success, start failure, stop timeout, force-termination failure and residual-resource state.
18. **Dependency direction:** Runtime must not import TUI, concrete Application use cases, Git/GitHub, Persistence, or Launch Discovery implementation packages.

These are proposed requirements only; this review does not freeze the BC.

## Error and safety semantics

Safety-critical Runtime errors are those where resource ownership may remain unresolved. They must not be collapsed into a generic string while marking state terminal.

At minimum Runtime should distinguish:

- invalid/unsupported start spec;
- failed process creation;
- failed containment assignment;
- failed PTY/ConPTY creation;
- unsupported capability;
- unknown SessionID;
- graceful-stop timeout followed by successful force stop;
- force-stop failure / residual live tree;
- cleanup timeout;
- PTY close/read/write/resize errors;
- shutdown aggregate failure.

A successful Stop result is a strong safety assertion: owned processes/resources are quiescent according to the platform contract.

## Tests / observability gaps

Current launch tests verify bounded logs, exit code, direct-process Stop and multiple sessions. Current terminal tests only cover text normalization, environment replacement and shell override. They do not establish the required Runtime safety contract.

Required future tests:

### Cross-platform contract tests

- Start success creates one queryable SessionID and expected capabilities.
- failed Start cleans all partial resources and emits one terminal result.
- Stop is idempotent.
- stopping already-exited session is deterministic.
- `stopped` is not observable until termination is confirmed.
- Restart creates a new ID only after old resource is quiescent.
- simultaneous Stop/Restart ordering is deterministic.
- StopAll attempts every session and aggregates failures.
- shutdown prevents concurrent new Start.
- program-exit cleanup invokes Runtime shutdown and surfaces residual-resource failure.
- session IDs never collide across launch/terminal kinds.
- capability misuse returns explicit unsupported error.
- output buffering stays bounded under concurrent writers/readers.
- event ordering/exactly-once completion.
- cancellation during Start, graceful Stop, force escalation and shutdown.
- `go test -race` coverage for registry/session/output/event paths.

### Windows-specific tests

- child/grandchild process tree is terminated by Stop.
- process that spawns descendants cannot escape the owned Job Object/equivalent contract.
- StopAll terminates multiple trees.
- restart leaves no old descendant alive.
- application-exit shutdown leaves no owned process tree.
- ConPTY handles/goroutines close deterministically.
- force-stop fallback after grace timeout.

### Unix-specific tests

- child/grandchild process group is terminated by Stop.
- graceful group signal followed by force group kill when ignored.
- process-group/session-group setup is correct for non-PTY sessions.
- PTY foreground/session-group behavior remains usable for interactive shell.
- no orphan descendants after restart/StopAll/exit.
- PTY descriptors and goroutines close after natural exit and explicit stop.

### Observability

Tests need diagnostics that can report SessionID, root PID, process-group/job identity (test/debug only), lifecycle phase, operation ID, exit cause and residual cleanup state. OS handles must not leak into Application API merely for observability.

## Unresolved questions

These questions should be resolved by Refactor Design / Application+Domain reviews, not guessed here:

1. Whether pure semantic `SessionID`, lifecycle enum and capability vocabulary live in Domain or Application API. Runtime must not own the upward-facing DTO package either way.
2. Exact Windows Job Object creation/assignment strategy and compatibility with the selected PTY/ConPTY library.
3. Exact Unix signal sequence (`SIGINT`, `SIGTERM`, then `SIGKILL`) for non-interactive launches versus PTY sessions.
4. Whether terminal Ctrl+C is modeled as ordinary PTY input bytes, explicit foreground interrupt capability, or both.
5. Whether Runtime exposes raw byte output, normalized line output, or both. Presentation semantics must remain out of lifecycle ownership.
6. Session-history retention/removal policy after completion.
7. Exact grace/force timeout defaults and configurability.
8. Whether optional foreground-job observation is worth implementing. It must not block the core Runtime contract.

None of these unresolved points justify keeping the current split-manager/direct-child lifecycle architecture.
