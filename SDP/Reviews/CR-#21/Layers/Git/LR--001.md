## Layer responsibility

### Git must own authoritatively

Git should authoritatively own local repository facts and local Git mutation mechanics, including:

1. repository root/identity as observed by Git;
2. worktree inventory and per-worktree HEAD/branch/detached state;
3. branch/ref/tag/remote-tracking ref existence and exact object IDs;
4. configured upstream relation as local Git configuration/fact;
5. local ahead/behind relation against a specific locally observed upstream ref;
6. explicit freshness metadata for observations that depend on remote-tracking refs;
7. status/index/worktree facts, including staged/modified/untracked/conflicted paths;
8. stash inventory and exact stash object identity;
9. commit history, graph topology, refs and local decorations;
10. local diff facts and bounded patch transport;
11. worktree creation/checkout/switch mechanics;
12. fetch/refspec mechanics, including exact ref verification when Application supplies expected identity;
13. stage/unstage/commit/stash/apply/pop/drop/restore/pull/push mechanics;
14. branch occupancy across registered worktrees;
15. typed safety/precondition failures and post-mutation verification facts;
16. mutation result state sufficient for Application to know whether a failed/cancelled command left state known, unchanged, changed, or indeterminate.

### Git must NOT own

Git must not own:

- TUI focus, modal or selection state;
- Application `OperationID`, user-intent supersession or confirmation UI lifecycle;
- GitHub API truth or the canonical reconciliation of Git local/upstream facts with GitHub branch/PR facts;
- product policy such as which selected object should be deployed, whether to stash before deploy, or whether a result should move UI focus;
- launch/runtime/process-session lifecycle;
- persistence of active-worktree preference;
- human-facing presentation strings as semantic read-model truth;
- cross-source graph annotation with GitHub PRs;
- destructive confirmation authorization merely because a Git status happened to be clean at some earlier time.

## Challenge of known findings

### BR21-M02 — confirmed and strengthened to a direct branch-deploy correctness risk

`ensureBranchStart()` returns an existing local branch immediately and only fetches `origin/<branch>` when that local branch does not exist. Therefore branch resolution has two materially different freshness semantics hidden behind one method.

At v0.3.14, the TUI branch deploy target contains both branch name and selected SHA, but `DeployBranchDetached` calls `CheckoutBranchDetached(path, branch)`, which ultimately uses `ensureBranchStart(branch)` and ignores the selected SHA. If the local branch already exists behind the GitHub-selected branch, Git can deploy the stale local tip while the UI selection represented a newer GitHub SHA.

This is not merely a presentation ambiguity. The selected branch identity can be materially different from what is checked out.

Required correction at design/contract level: Application must state whether a branch operation targets local branch truth, remote-tracking observation, or a GitHub-selected expected SHA. Git must expose primitives that resolve/fetch that exact requested source and verify an expected object ID where supplied.

### BR21-M03 — confirmed

`graph.Reader.Load` correctly performs useful local Git reading, but also accepts concrete GitHub PR and worktree DTOs and annotates commits. The Git layer should instead return local commit graph, refs, HEAD and remote-tracking observations only. Application performs PR/worktree joins; TUI View formats decorations.

### BR21-M07 — confirmed and refined

`worktree` contains both strong Git safety mechanics and product workflow semantics. The package must not be moved wholesale. `Deploy`, `CreateBranchWorktreeAs`, `CheckoutBranchWorktree`, `CheckoutBranchDetached`, PR convenience history and portions of PR preparation encode use-case choices above raw Git mechanics.

### APP29-H03 — confirmed

Application requires a canonical local/upstream/GitHub read model. Current Git facts are insufficiently explicit because `Status.UpstreamSHA` silently stays empty when resolution fails, while `Ahead/Behind` remain zero-valued. A configured-but-gone/unresolved upstream can therefore be indistinguishable from an equal relation to callers that inspect only current fields.

### APP29-H06 — confirmed and strengthened

Application needs confirmation/precondition identity. Current Git methods commonly re-check only coarse state (`Clean`, path still changed) rather than the exact state the user confirmed. Stash destructive operations additionally use positional `stash@{n}` refs. The Git port must provide stable precondition fingerprints and typed mismatch results.

## Authoritative Git fact model

The target Git port should report explicit facts rather than infer product meaning.

### Repository/worktree facts

Conceptually:

```text
RepositoryFacts
  RepositoryRoot
  ObjectFormat
  Remotes[]
  Worktrees[]

WorktreeFacts
  WorktreeID/path
  HEAD object ID
  HeadMode: Branch | Detached
  BranchRef? 
  Primary
  CurrentRelativeToAdapterRoot
  Locked + optional reason
  Prunable + optional reason
  StatusFingerprint
```

`Primary`/`Current` remain local Git/composition observations, not UI focus.

### Branch/upstream facts

A branch fact must distinguish at least:

```text
LocalBranchRef
LocalTipOID
ConfiguredUpstreamRef?      // configuration fact
UpstreamObservationState    // none | resolved | gone | unresolved
RemoteTrackingOID?          // local cached observation only
Ahead? Behind?              // only valid when comparison resolved
ObservationFreshness
```

Detached HEAD is not a branch with an empty name; it is an explicit mode.

Unpushed commits are a relation, not a boolean guessed from GitHub SHA. Locally, Git can report commits reachable from local branch and not from the resolved upstream observation. Application combines this with GitHub facts and freshness.

### Freshness model

Remote-tracking refs are **local observations**, not remote truth.

Git should expose freshness metadata such as conceptually:

```text
Freshness
  Kind: Unfetched | CachedObservation | Refreshed
  Generation/FetchID
  Remote
  ObservedAt (optional if deterministic clock policy allows)
  RefScope
```

The exact representation belongs to Refactor Design/BC, but the semantics are mandatory:

- merely finding `refs/remotes/origin/x` does not make it current;
- after a successful fetch of the relevant ref/scope, Git may mark that observation as refreshed for that fetch generation;
- Application decides whether a use case requires refreshed facts;
- GitHub API facts remain separate and are reconciled by Application.

### Required explicit upstream states

At minimum:

- no configured upstream;
- configured upstream resolved locally;
- configured upstream ref gone;
- configured upstream cannot be resolved/inspected;
- detached HEAD/not applicable.

Ahead/behind is valid only for a resolved local comparison and must not default semantically to zero when unknown.

## Which operations require freshness

The layer should not globally auto-fetch before every operation. Application defines the use-case requirement; Git provides explicit mechanisms.

### Fresh remote observation generally required

- deploying a branch selected from GitHub/remote semantics;
- creating/checking out a worktree intended to represent current remote branch tip;
- comparing local-vs-upstream for a user decision that claims current remote relation;
- PR/base range preparation where remote base correctness matters;
- decisions whether pull/push is needed when UI claims current state.

### Exact expected identity is stronger than generic freshness

For PR deployment, current code demonstrates the preferred pattern: fetch exact ref, resolve OID, compare to selected expected SHA, refuse on mismatch.

Branch operations sourced from GitHub should use the same principle where possible: Application supplies branch/ref scope plus expected object ID; Git fetches/observes the appropriate remote ref and verifies it before mutation.

### Operations that need not fetch

- local-only history of an explicitly supplied local ref/OID;
- local diff/status/staging/stash operations;
- checkout to an explicit local commit OID when no remote-current claim is made.

The result must remain labeled as local/cached where appropriate.

## Safe mutation / precondition / error model

### General invariant

> A Git mutation must either prove that the preconditions under which the user/Application authorized it still hold, or refuse with a typed stale-precondition result. If execution is interrupted after mutation may have started, Git must not claim unchanged state unless it has verified that fact.

### Precondition fingerprint

For confirmation-sensitive operations, Git should be able to create/revalidate a token/fingerprint containing the semantic target facts needed by that operation. Examples may include:

- repository/worktree identity;
- current HEAD OID and branch/detached mode;
- status/change-set digest;
- specific path state/digest for restore;
- index/worktree relation as needed;
- target branch occupancy set/generation;
- expected target OID;
- stash object OID and current ref mapping;
- relevant freshness/fetch generation.

Application owns the confirmation protocol and `OperationID`; Git owns revalidation of Git facts represented by the token.

### Typed result/error classes

The later port should distinguish at least:

- `NotFound` / missing ref/worktree/stash;
- `InvalidInput`;
- `DirtyWorktree`;
- `ConflictPresent`;
- `UntrackedPathRefusal`;
- `BranchOccupied` with occupying worktree;
- `PrimaryWorktreeRefusal` where policy remains in Git primitive contract;
- `DetachedHead` / `NoUpstream`;
- `UpstreamGone` / `UpstreamUnknown`;
- `NonFastForward` / rewind refusal;
- `ExpectedOIDMismatch`;
- `StalePrecondition`;
- `UnsupportedState`/locked worktree;
- `CancelledUnchanged` when verified;
- `CancelledStateIndeterminate` / `MutationStateIndeterminate` when mutation may have partially applied;
- transport/process error with preserved Git stderr diagnostics.

Human-readable error rendering belongs above Git.

## Safety review by operation

### Worktree create/checkout/deploy

Current strengths:

- absolute path validation;
- primary worktree refusal in retarget paths;
- dirty guard;
- branch occupancy checks in important PR/deploy paths;
- exact PR SHA verification;
- no silent rewind in `CheckoutRef`;
- post-checkout HEAD/clean verification;
- detached unreferenced commit protection in legacy deploy.

Required target improvements:

- unify typed preconditions;
- expose locked/prunable facts;
- branch operations must declare local/cached/refreshed/expected-OID source;
- revalidate authorization-sensitive facts immediately before destructive ref/worktree transition;
- return post-mutation authoritative facts.

### Dirty worktrees / restore

`RestorePaths` correctly refuses untracked and conflicted paths. That safeguard should be retained.

However, confirmation of “discard this changed path” must bind to the exact path state the user inspected. Re-checking only that it is still changed is insufficient to protect edits made after confirmation.

### Stash

Stash is repository-global across worktrees; that fact is correctly documented in current code.

Required target safety:

- identify stash by stable OID plus observed ref;
- before apply/pop/drop, verify the ref still resolves to the confirmed OID, or operate using an exact stable identity if Git supports the requested operation safely;
- dirty target guard before apply/pop remains;
- conflicts after apply/pop are legitimate mutation results, not generic success/failure ambiguity;
- drop is irreversible at product level and requires exact confirmation identity.

### Pull

Current `pull --ff-only` plus clean-worktree and upstream checks are appropriately conservative. The port should retain fast-forward-only default unless a later product requirement explicitly changes it.

Cancellation after pull begins must be treated as potentially indeterminate until repository state is re-read.

### Push

Current code does not force push, which is safe. Target result should state what ref was attempted, whether upstream was set, and refreshed local facts after success/failure where knowable. Force-push, if ever introduced, requires a separate explicit Application use case and BC safety contract.

### Stage/unstage/commit

Path validation is good for selected-path operations. Application sequencing such as “stage all then commit” belongs in Application. Git should return exact resulting commit OID and post-operation index/worktree facts as needed.

## Cancellation semantics

### Reads

Read-only Git commands may normally honor context cancellation directly. Cancellation yields no product mutation and can return a typed cancelled result.

Examples: status, list worktrees, refs, history, diff, graph, stash list/patch.

### Mutations

Mutation cancellation is different.

Because `process.ExecRunner` uses `exec.CommandContext`, cancellation can terminate a Git subprocess after it has changed refs/index/worktree/files. Application therefore must not interpret context cancellation as rollback.

For mutating operations:

1. define whether cancellation is accepted before command start only, cooperative during command, or converted into “stop waiting but reconcile later” semantics;
2. if the subprocess is killed after start, Git must re-read sufficient repository facts before classifying outcome;
3. if exact outcome cannot be proven, return `MutationStateIndeterminate` plus recovery/refresh requirement;
4. Application then emits exactly one terminal operation result without fabricating rollback.

The exact policy may vary by primitive, but the BC must make it explicit.

## Requirements for `BC--Application--Git.md`

The later BC must require at minimum:

1. Application owns all vertical use-case sequencing and `OperationID` lifecycle.
2. Git owns local repository/ref/worktree/stash truth and mechanics.
3. GitHub facts never enter Git adapter APIs as concrete GitHub DTOs.
4. Remote-tracking refs are explicitly local observations and never presented as inherently fresh remote truth.
5. Every upstream relation includes explicit state: absent/resolved/gone/unresolved and valid/unknown ahead-behind semantics.
6. Successful fetch returns a freshness/correlation identity for the observed ref scope.
7. Operations that claim an exact selected remote/PR/branch identity support expected-OID verification.
8. Confirmation-sensitive mutations support exact precondition identity and revalidation; stale precondition refuses without destructive action.
9. Stash destructive operations bind confirmation to stable stash object identity, not positional ref alone.
10. Restore/discard binds to exact confirmed path/change state and refuses if it changed after confirmation.
11. Dirty/untracked/conflict safety invariants are explicit and typed.
12. Branch occupancy across worktrees is queryable and mutation failures identify the occupying worktree.
13. Worktree facts include detached/primary/current and relevant locked/prunable availability facts.
14. Pull remains fast-forward-only unless a separately reviewed contract changes it.
15. Push is non-force by default; force operations require a distinct explicit contract/use case.
16. Read cancellation is safe and straightforward; mutation cancellation has explicit effect-state semantics and may return indeterminate state requiring reconciliation.
17. A cancelled/failed mutation must never be reported as unchanged unless Git has verified unchanged state.
18. Mutation success returns authoritative post-state sufficient for Application projection/reconciliation.
19. Git port DTOs contain semantic facts, not TUI formatting strings.
20. Graph cross-source joins remain Application-owned; diff/graph textual decoration remains TUI View-owned.
21. Adapter-specific parser/process structs remain private to Git.

## Unresolved questions for Refactor Design / later focused reviews
