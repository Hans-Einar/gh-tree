This review independently evaluates the horizontal **TUI State** responsibility at the frozen `v0.3.14` product SHA. Governance/review/documentation commits after the frozen product SHA are treated as process authority only and are not evidence of product change.

## Layer responsibility

### TUI State must own authoritatively

TUI State should be the **single authoritative owner of ephemeral interaction intent**:

1. current top-level presentation mode/view identity;
2. active pane;
3. active subpane within a pane;
4. keyboard focus target;
5. selection identity/cursor within currently projected lists;
6. scroll positions that are interaction state rather than renderer-computed layout;
7. open modal identity and modal-local selection/input state;
8. search/filter input and whether search editing is active;
9. console-tab selection and whether console input currently owns keyboard focus;
10. user intent to auto-follow an operation result, represented explicitly and supersedable;
11. local, non-authoritative view projections derived from Application read models/events;
12. correlation state needed to reject stale async results (`operationID`, intent generation/token, request generation);
13. deterministic reconciliation rules when refreshed data removes the selected semantic item.

The layer may expose a pure transition of the form:

```text
(State, Action|ApplicationEvent) -> (State, []Effect)
```

where an `Effect` is a declarative request to Application or the Bubble Tea host, not a direct backend call.

### TUI State must NOT own

TUI State must not own or execute:

- Git/worktree/stash mutation or authoritative Git facts;
- GitHub API facts or mutations;
- deploy/stash/commit/push/pull workflow sequencing;
- active-worktree durable persistence;
- launch discovery implementation;
- process/session/PTY lifecycle, process snapshots as authoritative runtime truth, process selection side effects or resize/write implementation;
- global operation lifecycle truth beyond UI projection/correlation;
- creation of independent `context.Background()` operation lifetimes;
- Lip Gloss styles, color palette, panel geometry, layout joins, modal compositing or activity glyph animation;
- adapter-specific DTOs as its durable public model;
- cross-source reconciliation such as local branch vs upstream/GitHub tip.

## Why console start/restart steals focus after Alt+N or Tab

The sequence is deterministic and does not require a data race:

```text
T0 user presses F5 / Alt+T / F6
   -> TUI creates async command using context.Background()
   -> no intent generation is attached

T1 user presses Alt+N or Tab before command completes
   -> current state correctly moves focus to Navigator/Worktrees/etc.

T2 async start/restart/open returns
   -> consoleStarted312Msg / consoleRestarted312Msg / terminalOpened313Msg
   -> handler cannot know T1 happened
   -> handler calls selectConsoleID312(...)
   -> sets consoleFocus=true
   -> start/open also sets focus=paneDetails

Result: older operation completion overwrites newer user intent.
```

This is an event-ordering bug, not a goroutine-memory race. Bubble Tea serializes message handling, but serial handling alone does not give semantic causality. The reducer needs causality metadata.

## Target authoritative TUI State model

The replacement must not copy the V310..V314 chain into `internal/tuistate/`. It should introduce one state authority with explicit typed substate.

A target shape is conceptually:

```go
type State struct {
    Screen       ScreenState
    Focus        FocusPath
    Navigator    NavigatorState
    Worktrees    WorktreeUIState
    Active       ActivePaneState
    Console      ConsoleUIState
    Modal        ModalState
    Search       SearchState
    Operations   OperationCorrelation
    Projection   Projection
    Notices      []Notice
}
```

Key properties:

- `FocusPath` is one authority, e.g. `{Pane, Subpane, InputTarget}`; no independent `consoleFocus`/`stashFocus` booleans.
- `ModalState` is a sum type (`None | ExitConfirm | WorktreeChooser | DeployConfirm | StashConfirm | StashPatch | ...`) with modal-local selection/input and optional operation correlation.
- `ConsoleUIState` owns selected **console ID**, scroll and input focus intent. It does not own process truth.
- `Projection` contains immutable/replaceable Application DTOs with generation/source IDs, never concrete adapter objects.
- `Operations` contains only IDs/tokens needed for UI correlation and desired auto-follow behavior. Application owns actual operation lifecycle.
- selection should prefer semantic IDs (branch name, PR number, worktree ID/path, commit SHA, console/session ID, stash ID) over raw indexes; render-time indexes are derived.
- invalid combinations are rejected/normalized centrally.

### Deterministic reducer model for Bubble Tea

Recommended interaction pattern:

```text
Bubble Tea KeyMsg / Window semantic action
        |
        v
   map key -> Action
        |
        v
  tuistate.Reduce(State, Action)
        |             \
        |              -> []Effect (Application commands, quit, timer request)
        v
     State'

Application Event/Result
        |
        v
  tuistate.Reduce(State, Event)
        |
        +-- validate operation/generation/intent correlation
        +-- reject stale event if superseded
        v
     State'
```

The Bubble Tea host executes Effects and converts Application events back into reducer events. Direct backend interfaces disappear from TUI State.

## Async ordering / supersession contract

Three identifiers solve different problems and should not be conflated.

### 1. Operation ID

Application assigns a unique `OperationID` to every asynchronous use case invocation (`Deploy`, `StartConsole`, `DiscoverLaunch`, `LoadDiff`, `Refresh`, `StashApply`, etc.). Every progress/terminal event carries it.

Purpose:

- match completion to the operation that caused it;
- ensure exactly one terminal result per operation;
- prevent operation A from clearing operation B's presentation state;
- correlate confirmation workflows.

### 2. Request/data generation

Repeatable queries whose newest answer supersedes older answers carry a generation/request ID scoped to the query key, e.g.:

- repository refresh generation;
- active-worktree status generation keyed by worktree identity;
- launch discovery generation keyed by active worktree;
- stash-list generation keyed by worktree;
- branch-history generation keyed by branch;
- diff generation keyed by requested source;
- commit-page generation/source identity.

A result is accepted only if its generation is still current for that projection slot.

### 3. User-intent token / navigation generation

Every user action that changes navigation/focus/modal/console selection increments a monotonic `IntentGeneration` (or issues a scoped token). An operation may capture the generation when started and declare a **conditional UI follow-up**, such as “auto-select the newly opened terminal if this intent has not been superseded.”

At completion:

```text
if result.IntentToken != state.CurrentIntentToken {
    apply operation/projection result only;
    reject navigation/focus/modal/selection follow-up;
}
```

For most operations the event should contain no navigation follow-up at all.

### Core invariant

> **A background completion may update only the operation/projection state it owns. It must never overwrite newer independent user intent. Focus, active pane, subpane, modal identity and console-tab selection change only from a current user intent or from an explicitly declared conditional follow-up whose intent token is still current.**

This should become a frozen requirement in `BC--TUIState--Application.md` later.

## Allowed async mutations by state class

| State class | Background completion allowed? | Rule |
|---|---|---|
| focus | normally **NO** | only a conditional focus follow-up with matching unsuperseded intent token |
| active pane | normally **NO** | navigation should occur synchronously when user invokes it, not when data arrives |
| subpane | normally **NO** | same as pane; reconcile only if current subpane ceases to exist |
| selection | limited | preserve selected semantic ID; if removed by accepted refreshed projection, deterministically choose nearest/first valid item without moving focus |
| modal identity | limited | Application may emit `RequiresConfirmation` for the current operation; modal opens only if op is still current and no newer modal/navigation intent superseded it; terminal result closes only the modal bound to that exact op |
| console-tab selection | conditional | new console may auto-select only when a captured auto-follow intent token remains current; stop may choose deterministic fallback if selected session disappeared, but must not move pane focus |
| scroll | generally **NO** | reset only when the user changes selected semantic item or explicitly opens a new still-current view; stale data result cannot reset scroll |
| cached projection | **YES**, correlated | only if generation/source/op matches current slot |
| operation status/notice | **YES**, correlated | status from stale operation may be logged/history, but must not overwrite current primary status if a newer operation/intent owns it |

## Cancellation semantics

TUI State should never create ad hoc `context.Background()` for use cases.

Required direction:

1. Composition owns the application/root lifetime context.
2. TUI State emits an Application command descriptor.
3. Application creates/tracks operation lifetime and `OperationID`.
4. If user intent explicitly cancels an operation, TUI emits `CancelOperation{ID}`.
5. If a newer query supersedes an older query, Application may cancel the old operation; TUI will still reject any late terminal event by generation.
6. Closing gh-tree cancels/finishes Application operations under the global lifecycle contract; Runtime cleanup remains Runtime/Application authority.
7. Cancellation is observable as one terminal operation event (`Cancelled`, `Completed`, `Failed`) and must be idempotent.

Ignoring stale results remains necessary even with cancellation because cancellation is not guaranteed to prevent a result already in flight.

## Incoming boundary requirements — Application -> TUI State

Application should supply only stable Domain/Application DTOs/events, not concrete `worktree`, `launch`, `github`, `diff` package types.

Required event properties:

- every async operation event carries `OperationID`;
- repeatable read/query results carry request generation and query/source identity;
- session events carry stable `SessionID`;
- active-worktree events carry stable Worktree identity/path as domain/application data;
- terminal/runtime capabilities are explicit fields, not inferred from provider strings;
- errors are typed/semantic enough for TUI to select a user action/modal, while human formatting remains presentation-owned;
- `RequiresConfirmation` is explicit and tied to the operation/request that requires it;
- no Application event contains an unconditional imperative like “focus console”;
- result events are safe to ignore when stale.

## Outgoing boundary requirements — TUI State -> Application

TUI State should emit declarative command intents carrying stable identities:

- repository/worktree/PR/branch/commit/stash/session IDs, not list indexes;
- the current operation being confirmed/cancelled when applicable;
- input values collected by a modal/form;
- no Lip Gloss/Bubble Tea types;
- no concrete adapter DTOs;
- no context construction;
- no callback functions that let Application mutate TUI state.

Command submission returns/associates an `OperationID`. TUI stores only correlation metadata and requested auto-follow semantics.

## Proposed `BC--TUIState--Application.md` requirements

The later contract should require at minimum:

1. **Single interaction authority:** Application never directly mutates TUI focus/selection/modal state.
2. **Command/event boundary:** TUI emits typed Application commands/queries; Application emits typed results/events.
3. **No concrete adapter leakage:** DTOs crossing the boundary are Domain/Application-owned.
4. **Operation identity:** every async use case has stable `OperationID`; exactly one terminal result.
5. **Query generations:** refresh/discovery/history/diff/status/list results are versioned/scoped so stale results can be rejected.
6. **Intent supersession:** conditional navigation/focus/modal follow-ups carry the originating TUI intent token; mismatched tokens are ignored.
7. **Background invariant:** a completion cannot overwrite newer independent user intent.
8. **Confirmation protocol:** `RequiresConfirmation{OperationID,...}` and `Confirm/Cancel{OperationID,...}`; a result cannot close a different/newer modal.
9. **Cancellation:** TUI requests cancellation by operation ID; Application owns contexts/lifetimes; late results remain safely rejectable.
10. **Session identity:** runtime session events use stable `SessionID`; session facts are authoritative outside TUI.
11. **Active worktree:** TUI requests `SetActiveWorktree`; Application owns session transition and persistence coordination.
12. **Error semantics:** typed classification/capability/actionability separate from human presentation text.
13. **Determinism:** given the same TUI state and ordered command/event stream, TUI transitions must be deterministic.
14. **No backend callbacks:** Application cannot receive TUI persistence callbacks or UI-mutating closures.
15. **No hidden selection coupling:** console tab selection is TUI-local unless an explicit input-routing command is semantically required.

## Proposed `BC--TUIState--TUIView.md` requirements

The later contract should require at minimum:

1. TUI View is render-only and receives an immutable presentation/view model.
2. TUI View cannot call Application, Git, Runtime, Persistence or mutate TUI State.
3. Focus is represented semantically by one authoritative focus path supplied by TUI State.
4. Selection is represented by stable selected identity plus ordered projected rows; View does not decide product selection.
5. Modal identity/content/action affordances are supplied semantically; View chooses layout/style only.
6. View owns color, borders, mnemonic styling, truncation/wrapping, responsive layout and overlays.
7. View owns animation frame/timer presentation policy; operation truth is supplied as semantic state (`Busy`, `Running`, etc.).
8. View reports measured terminal-console viewport size through a presentation/host event if Runtime resize needs it; State does not recreate layout math.
9. Help/footer text is derived from available semantic actions/keymap, not duplicated hard-coded behavior across wrappers.
10. Rendering is pure for a given view model + viewport; it must not mutate global styles or state.
11. `graphui` must use the same view-state contract rather than a separate Bubble Tea controller architecture.
12. No async completion is handled by View.

## Lifecycle / concurrency

TUI State itself should own no OS resource lifecycle. Its concurrency responsibility is **ordering and supersession of events**.

Required invariants:

- event handling is serial/deterministic;
- operation/request identity is explicit rather than inferred from booleans or paths;
- accepted projection update is atomic from the reducer's perspective;
- a stale event can be ignored without side effects;
- cancellation and completion may race, but only one Application terminal operation outcome is authoritative and TUI still validates correlation;
- timers used only for animation are View concerns;
- polling/subscriptions for runtime facts are Application/Runtime concerns, not self-rescheduling state commands;
- no result handler may schedule an unbounded poll merely because a provider string or cached state suggests activity.

## Error and safety semantics

1. A failed/stale operation must not clear or close a newer modal.
2. A failed/stale operation must not change active pane/focus/console tab.
3. Destructive action confirmation is tied to an exact operation/target identity; changing target invalidates the confirmation.
4. Deploy/stash/restore confirmation must display the exact semantic target delivered by Application, not a mutable adapter object retained across arbitrary refreshes.
5. If selected data disappears after refresh, TUI reconciles selection deterministically without performing product mutation.
6. Persistence errors are Application events/notices; the TUI must not pretend the durable change succeeded if Application reports failure.
7. Runtime stop/restart errors update the matching session/operation projection but cannot redirect focus.
8. User cancellation of a modal supersedes later `RequiresConfirmation`/payload results for that modal intent unless a new explicit request is made.

## Missing tests / observability gaps

Existing tests cover individual navigation keys, some render content, launch-stack behavior, console tab selection and terminal key byte mapping. They do **not** cover the causality contract required by the architecture.

Required tests for target TUI State include:

### Stale async results

- start console -> Alt+N -> late `ConsoleStarted`: focus remains Navigator;
- start console -> Tab -> late completion: current pane remains user-selected;
- restart console A -> select console B -> late restart A: selection remains B;
- open terminal -> navigate away -> late open: terminal may appear in projection but does not steal focus;
- launch discovery request A -> active worktree changes -> late A result rejected;
- stash list/patch request A -> worktree/modal changes -> late A result rejected;
- branch history request A -> select different branch -> late A result rejected;
- diff request A -> leave diff/open other mode -> late A result cannot force mode back to diff;
- refresh generation N -> refresh N+1 -> N arrives last: N rejected.

### Focus preservation / navigation

- rapid Alt+N/W/A/O/L/S sequences with interleaved async events;
- repeated Tab and reverse-Tab across all panes;
- Tab routing while an interactive terminal has input focus versus application-global shortcuts;
- pane/subpane transition table with every valid state and no impossible combination;
- focus preserved when selected external item disappears and fallback selection is chosen.

### Modal ownership

- only one modal active at a time;
- a terminal result closes only the modal tied to its `OperationID`;
- user Esc/cancel increments/supersedes intent so late patch/discovery/confirmation result cannot reopen modal;
- changing deploy/stash target invalidates old confirmation;
- modal-local cursor/input cannot leak into next modal type.

### Console selection

- selected console ID survives snapshot reorder;
- removal of selected console chooses deterministic fallback without pane-focus steal;
- new console auto-select only with still-current auto-follow token;
- restart that returns same/new session identity obeys explicit contract;
- Runtime does not need UI tab selection to maintain session truth.

### Deploy/stash completion ordering

- deploy A then newer operation/intent B: late A result cannot clear B busy/modal/status authority;
- stash mutation completion cannot clear a newer stash confirmation;
- deploy result cannot mutate cached worktree projection if superseded by newer refresh generation without reconciliation through Application;
- confirmation target identity remains stable from prompt to command.

### Deterministic reducer

Table-driven tests should assert exact `(state, action/event) -> state/effects` transitions without goroutines, real Git, Runtime, filesystem or Lip Gloss. The same ordered event stream must always yield identical state/effects.

### Boundary enforcement

Future CI should ensure `internal/tuistate/` does not import concrete `internal/git`, `internal/github`, `internal/runtime`, `internal/launchdiscovery`, `internal/persistence`, old `internal/worktree`, old `internal/launch`, Lip Gloss, or concrete Application implementations.

## Unresolved questions for Refactor Design / later focused reviews

1. Should `IntentGeneration` be one global monotonic generation or scoped generations (navigation, modal, console selection)? A global generation is simpler and safer; scoped tokens reduce false supersession. Refactor Design should choose one model and document it.
2. Should opening a newly started console auto-focus by default? Current behavior does. Architecture can preserve it as a conditional auto-follow intent, but UX policy belongs to accepted design, not this review.
3. Should graph be an in-main-TUI screen or remain a separately launched Bubble Tea program? Either choice must reuse the same state/boundary architecture.
4. Which stable Application DTOs represent navigator tree rows versus Domain objects? TUI State should not reconstruct cross-source semantic joins, but it may still build purely presentational grouping/filtering from an Application read model.
5. Does active-worktree selection need optimistic UI projection before Persistence succeeds, or should the UI change only after `ActiveWorktreeChanged`? Refactor Design/Application review should define failure semantics.
6. How should status/notifications be modeled so late operation notices remain observable without overwriting the current primary interaction status? A notice/event queue is likely preferable to one mutable string.
7. Which keymap layer maps Bubble Tea `KeyMsg` to semantic actions and handles interactive terminal byte forwarding? The state/view split should keep terminal bytes out of the pure reducer where practical while preserving one focus authority.
8. Whether terminal viewport resize events originate from TUI View or the Bubble Tea host needs coordination with TUI View and Runtime reviews.

## Disposition

`ACCEPTED — FOCUSED REVIEW COMPLETE / REFACTOR NOT AUTHORIZED`

The TUI State target layer remains valid, but its implementation must be a redesigned single deterministic state authority, not a relocation of the V310->V314 wrapper chain.

Key conclusions:

- TUI State authoritatively owns ephemeral user interaction intent: focus/pane/subpane, selection, modal state, search, console-tab selection and supersession/correlation state.
- Application/Runtime/Persistence own product operation, runtime and durable truth; TUI receives projections/events only.
- the current wrapper chain has overlapping focus/modal/operation authorities and direct vertical orchestration;
- async focus stealing is caused by semantically stale completions being allowed to mutate navigation with no intent token;
- stale-result rejection requires operation IDs + query generations + user-intent tokens, not more booleans;
- `graphui` should converge on/reuse the same state architecture;
- rendering/style/layout/animation leave TUI State entirely.
