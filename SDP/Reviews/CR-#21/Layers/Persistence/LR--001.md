## Layer responsibility

Persistence owns locating, reading, decoding, migrating and writing gh-tree-owned settings/state; storage scope enforcement, immutable snapshots, storage versions/conflicts, write resource cleanup and truthful persistence outcomes. The target is internal/persistence/ implementing Application-owned ports.

Application owns durable intent, active-worktree session context, validation against Git facts, save/default policy, operation ordering, publication and recovery choices. Launch Discovery owns provider semantic validation and resolution of stored launch intent. TUI State owns ephemeral focus, cursor, modal and query relevance. Composition supplies storage configuration and wires the adapters. Domain supplies opaque semantic values; it performs no filesystem canonicalization or serialization.

Persistence must not discover Git repositories, choose an active worktree, resolve launch commands, execute processes, decide focus, import concrete adapters, or silently repair user intent. Storage generations are not Application OperationID, Domain identity or launch source versions.

Migration must map old owner/name keys using verified selected context and preserve the original when host/clone/case mapping is ambiguous. Do not fan a local active path out to every clone sharing a remote, guess a different registered worktree, or delete colliding entries as a side effect of one setter. ## Filesystem path and permission policy

Three path classes need different rules: user-selected --config/--state locations, per-user default directories, and worktree-relative project storage. Do not apply a project sandbox to explicit user storage paths or reject intentionally linked home/XDG directories merely because a project-file link is unsafe.

For CLI overrides, preserve configurable locations and define relative paths against the startup directory exactly once; reject or explicitly resolve empty input instead of relying on incidental process cwd. For default locations, preserve existing platform placement and define invalid/relative environment-variable handling. Default paths are currently computed before parsing overrides (E5), so a default lookup failure prevents even a supplied override; Composition must settle startup ordering while preserving override capability.

For local identity, physical alias/case/volume handling belongs to Git/Composition's registered-root mapping. Persistence should receive an explicit scope and stable locator; blanket lowercasing, TrimSpace or filepath.Clean is not proof of file identity. Distinct case-sensitive paths must not collapse; valid spaces must survive; absolute, drive-relative, rooted, UNC/device and slash/backslash forms require platform cases. Empty worktree preference means absent/clear only if the accepted API says so, never implicit dot.

For project storage, recommend disallowing .gh-tree/run.json redirection outside the accepted concrete worktree root, with an explicit policy for in-root links, linked roots, reparse points and replacement during save. Validate storage parents and destination independently of provider dir. A lexical prefix check or untested EvalSymlinks call cannot establish Windows containment; accepted LD36 evidence already records that limitation. No blanket protection against arbitrary project script effects is promised.

Current state creates directories with 0700, writes with 0600 and then Chmod(0600); launch uses 0755/0644. Existing directory permissions are not repaired by MkdirAll. Existing launch-file permissions are not changed by WriteFile. State's chmod occurs after bytes changed and can itself fail. Go's Windows chmod controls the read-only bit, not a Unix-style owner-only ACL; the code does not prove a private Windows ACL. Preserve appropriate per-user privacy and committable-project readability through platform-tested creation/replacement rules; do not claim 0600 is a portable security boundary.

## Lifecycle / concurrency and atomicity

Persistence owns only bounded request-time files, temporary files and writer coordination. It owns no process/session registry. Current methods synchronously open/read/write/close and take no context; StateStore holds its instance mutex throughout I/O, including getters waiting behind a write. No background flush or shutdown flush exists.

Required save sequence, refined by platform design:

1. Receive explicit scope, intended field/document change and expected storage version (including expected absence). Validate structural data before touching old bytes.
2. Serialize cooperating writers for the actual storage object/scope, not only one Go object; load/revalidate under that coordination and check expected version.
3. Create a unique temporary file in the destination directory using safe exclusive creation and accepted permissions; write the complete document without changing the old file.
4. Flush/close as required by the promised durability level, then use a tested platform replacement primitive. Recheck accepted path/target identity at the defined boundary.
5. Establish required directory/metadata durability where supported; publish the committed snapshot/version and release resources. Clean only owned temporary resources, including failure paths.

Atomic visibility, process-crash recovery and power-loss durability are distinct promises. “Write then rename” alone does not establish all three, and generic Go os.Rename explicitly disclaims atomicity on non-Unix platforms. REFDES must select and test Windows replacement behavior and Unix flush/directory policy, including sharing violations and supported filesystems. No platform guarantee is frozen here.

A content fingerprint/version must reflect the whole stored document, including unknown fields. Expected-version checks plus cooperative locks prevent stale cooperating writers from silently replacing newer intent. An external editor need not honor those locks: rereading/version checks can detect changes but do not provide a universal atomic compare-and-swap against arbitrary noncooperating writers. Document the check-to-replace limit; do not claim stronger isolation from an in-process mutex or optimistic token.

Changes to unrelated keys may be merged only by the accepted Application/storage command semantics after fresh read; a stale whole snapshot is not a merge. Alias/default must commit together. No multi-file transaction spanning state.json and run.json is presently required by existing capability. Design should avoid inventing one unless a concrete selected Slice requires it.

Cancellation before commit leaves old bytes unchanged and cleans temporary resources. Cancellation after replacement is not rollback. Once a write may have committed, return committed or indeterminate/durability-uncertain state and reconcile before retrying. Application still delivers exactly one terminal operation outcome; Persistence does not allocate OperationID or decide UI supersession.

## Error, recovery and schema semantics

| Condition | Current behavior / required observable contract |
|---|---|
| Missing file/value | Loads currently default on os.ErrNotExist; getters return empty for absent and stored empty. Target result distinguishes Missing/document absence from valid empty data, preserving default policy in Application. |
| Malformed JSON / wrong field type | Load/OpenStateStore/LoadConfig return errors. Composition aborts startup; SaveCandidate refuses. Keep original bytes; do not substitute empty state then autosave. |
| Valid JSON, unsupported shape/version | null is accepted as empty by state/config; unknown fields/version ignored. Define valid envelope/schema and typed UnsupportedVersion/InvalidData; forward files must not be rewritten as old schemas. |
| Provider/default semantic error | Launch Validate currently rejects missing default alias, unknown provider and invalid provider options. Move semantic validation to Discovery through Application; persistence structural decoding must not normalize executable intent. |
| Permission, unavailable path, directory-as-file, I/O error | Raw errors are wrapped with read/write/path context in most paths. Preserve causes and distinguish operation stage; access denied is not Missing. Availability/fallback UX remains Application/Composition policy. |
| Precommit write failure | Target NotCommitted guarantees old bytes/cache unchanged. Current in-place writer cannot make that guarantee; even Chmod failure may follow successful byte write. |
| Replacement/postcommit failure | Return Committed with durability warning or Indeterminate according to evidence, never generic failure implying no side effect. Provide version/reload data needed for reconciliation. |
| Conflict / path rejection / cancellation | Typed outcomes, original intent preserved, no unconditional overwrite retry. Diagnostics identify store scope and stage without dumping configuration/command contents. |

Legacy compatibility requires a schema mapping for user config, navigation state and run.json separately. Retain explicit empty stripPrefixes versus absent/null default behavior; preserve worktree labels/paths/branches, lastFolders/lastWorktrees, aliases, default and all provider fields including command. No user config writer exists today, so unknown-field loss there is a future migration concern, not an observed current rewrite.

For writable documents, preserve unknown fields through read-modify-write where their schema allows it, or refuse unsafe writes to unsupported versions while leaving bytes intact. Do not invent defaults that overwrite forward/user-authored data. Future migrations must be idempotent, validated before commit, and recoverable through the accepted original-preservation strategy. Duplicate/case-colliding keys and ambiguous old scope require explicit deterministic disposition; silently choosing a winner is not a migration plan.

No automatic corruption repair is authorized. Application may offer the existing operation with an explicit unavailable-storage result or follow the accepted startup policy. Recovery must distinguish malformed bytes from unsupported-but-valid data, preserve the source and never create an unrelated approval workflow.
