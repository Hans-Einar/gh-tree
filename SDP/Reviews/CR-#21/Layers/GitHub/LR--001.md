### Creation target evidence and limits

GH43-H01 has a concrete source-level scenario: selected base repository upstream/project; local feature tracks contributor/project:feature; upstream/project also has feature. The cached Upstream nonempty guard passes and the adapter sends --repo upstream/project --head feature. The checked CLI semantics select upstream/project:feature. No publication was attempted. Server permissions, branch existence and existing-PR checks can refuse; the code does not prove the intended fork identity before submission.

The create use case currently expresses branch-based intent, not a user-selected immutable commit. Do not falsely claim it already promises exact local HEAD publication. REFDES must define its intended remote head from local context and visibly preserve that meaning; an exact-revision variant, where required by existing selected-revision intent, must retain ExpectedRevision. A configured upstream alone proves neither remote branch existence nor that current local commits were pushed.

GH43-M02 is independently visible in annotations and activation even without creation. A PR number is scoped to its base repository; head branch belongs to its head repository. Equal branch names are insufficient. Exact SHA equality establishes a commit-content association within accepted scope, not identity of a branch or unique PR. Multiple PRs can legitimately share a head/revision. The graph's SHA join is a useful content annotation; its ownership must move to Application without replacing it with name-only matching.

## Native CLI side effects and compatibility

Checked installed gh 2.96.0 (2026-07-02) help and its tagged primary source, in addition to current official manuals. Product does not pin a gh version; conclusions about native internals below are version-bounded and require supported-version verification during implementation.

**The supported invocation does not implicitly fork or push.** The official [gh pr create manual](https://cli.github.com/manual/gh_pr_create) states that explicit --head suppresses both. Tagged [NewCreateContext:769-803](https://github.com/cli/cli/blob/v2.96.0/pkg/cmd/pr/create/create.go#L769) returns skipPushRefs for that flag; [handlePush:1161-1188](https://github.com/cli/cli/blob/v2.96.0/pkg/cmd/pr/create/create.go#L1161) returns before fork/remote-edit/push mechanics. Removing --head or substituting the generic interactive create flow would weaken this guarantee. No dry-run probe was used: the CLI itself warns that dry-run can still push in other modes.

Explicit --title/--body (including empty body), --base and --head select the noninteractive submit path in [create.go:467-508](https://github.com/cli/cli/blob/v2.96.0/pkg/cmd/pr/create/create.go#L467). The CLI still reads local remotes/branch configuration in NewCreateContext; --repo allows missing Git-remotes context through [getRemotes:1023-1033](https://github.com/cli/cli/blob/v2.96.0/pkg/cmd/pr/create/create.go#L1023). These are read dependencies, not local Git mutation ownership. The adapter should require no local repository for remote facts or fully specified remote operations; current UI separately requires an active local branch for its creation flow.

The native request enables maintainer modification by default because the product omits --no-maintainer-edit; [flag mapping:267-268](https://github.com/cli/cli/blob/v2.96.0/pkg/cmd/pr/create/create.go#L267) and [submitPR:1035-1078](https://github.com/cli/cli/blob/v2.96.0/pkg/cmd/pr/create/create.go#L1035) carry that value. Record this existing behavior explicitly in the remote mutation contract; do not silently change it or invent a new UI setting. Normal PR publication can notify repository participants and trigger repository automation; draft does not mean private or effect-free. The REST create endpoint explicitly documents notifications and secondary-rate-limit exposure. [GitHub create-PR API](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request).

The CLI performs an existing-open-PR check for head/base before submission (create.go:475-488). That reduces duplicate creation but is neither a transactional idempotency key nor proof after an uncertain request. It also accepts user:branch heads, with documented organization-head limitations; the baseline TUI does not construct such qualification. Supporting an alternative transport may resolve those limitations only insofar as needed to preserve accepted use cases, not authorize new fork-management features.

Authentication remains the user's gh authentication, configured by host. No adapter auth-login/auth-refresh/setup-git mutation should be introduced. gh may maintain its own transport/config caches or emit diagnostics; those are distinct from gh-tree preferences or local Git. The [gh environment manual](https://cli.github.com/manual/gh_help_environment) documents host/token selection, stderr debug/update notices and prompt controls. Define deterministic noninteractive invocation and diagnostic handling without changing global user configuration or exposing tokens/title/body in logs.

## Freshness, completeness and reconciliation

An observation should identify the selected remote scope, query/filter/page scope, observation interval or captured time, opaque observation identity, completion/limit state, and any source failure. Application request generation and Git fetch generation are separate values; neither is derived from UpdatedAt. A PR can remain unchanged while a newer observation confirms it; a newly completed query can still reflect an earlier snapshot than another source.

No client cache exists today. App/TUI snapshots are caches/projections. A future adapter cache must expose cache origin/age/revalidation semantics rather than relabel cached data freshly observed. Request completion time alone must not authorize older projection replacement. Across independent pages or PR/branch/Git requests there is no atomic repository snapshot; preserve that limitation.

Keep finite bounds. The current PR maximum is a total retrieval cap; branch per_page=100 is one page, not a total inventory proof. [gh pr list](https://cli.github.com/manual/gh_pr_list), [GitHub list-branches API](https://docs.github.com/en/rest/branches/branches#list-branches). Define a bounded page/cursor or bounded aggregate result with Complete, MoreAvailable/Truncated or Unknown completeness; at the cap, absence cannot be inferred. Do not blindly add --paginate: gh emits separate page values unless explicitly wrapped, and an unbounded traversal defeats the current bound. [gh api pagination](https://cli.github.com/manual/gh_api).

Pagination must carry scope, deterministic ordering where supported, cancellation/budget behavior and duplicate/change handling. If the transport cannot prove exhaustiveness, report that fact. No automatic additional page-fetch UI is mandated by this review; design may retain a labeled bounded view, but existing navigation must not silently equate a limit with remote deletion. This also matters for persisting nearest namespace fallback and displaying no-PR relationships.

Application combines Git local tip/configured upstream/cached tracking tip/fetch generation with GitHub repository/branch/PR observations. Equal OIDs are one comparison fact; ahead/behind requires Git graph comparison against exact known endpoints. Differing scopes, absent upstream, inaccessible remote or limited lists yield explicit unknown/partial results, not zero/equal or deleted. Partial source policy remains APP29-M01: preserve diagnostics and choose usable projections deliberately; current Load discards all sources on one error.

The accepted Ref/Revision Authority rule is unchanged: when exact commit selection exists, retain it in the command; fetch/resolve mutable PR/branch locators only as mechanisms and verify they equal ExpectedRevision before mutation. Preserve the existing PR fetch comparison and generalize the branch path under GIT31-H01/DOM33-H01. A fresh GitHub observation cannot substitute for this check. GitHub never performs the local fetch, checkout or post-checkout verification.

## Lifecycle, cancellation, errors and mutation outcomes

Client state is just runner plus dir; it has no background workers, subscriptions or registry. Each query starts one gh command. The generic runner inherits process environment, uses CommandContext and collects output without a byte bound; no adapter deadline is imposed. Application must supply the root-derived operation context/deadline; transport closes/reaps owned command resources and bounds payload/diagnostic memory. Persistent launch/terminal cleanup remains Runtime, not this adapter.

Reads can normally be cancelled without product mutation. Still return a classified cancellation and no complete/freshness success; Application/TUI must reject late generations. Killing the CLI during PR creation is not remote rollback. The HTTP mutation may have reached GitHub before cancellation, connection loss, timeout, parse error or process termination. Client must never assert NotCreated merely because exit status is nonzero or URL parsing failed.

| Condition | Required remote boundary behavior |
|---|---|
| Invalid input/scope before execution | Typed invalid result, no invocation. Canonical validated repo must be the one actually passed; validate API-specific branch/head syntax without silently trimming identities into other targets. |
| Authentication / permission / unavailable repository | Preserve meaningful classification and safe cause; do not conflate unauthorized private repository with proven absence. |
| Rate limit / transient transport | Preserve retry-after/reset where available, bounded retryability and source scope; Application schedules any retry. No tight or automatic mutation retry. |
| Invalid API shape / unsupported capability or CLI version | Typed protocol/unsupported result; no zero-value facts or fabricated create success. |
| Pre-submission known rejection | No new creation when evidence establishes rejection; existing-PR response can carry a candidate identity for reconciliation, not automatic ownership of another user's PR. |
| Validated creation response | Created PR ID/URL, actual scoped head/base and known result facts; semantic success separate from later overview-refresh failure. |
| Request may have committed, outcome unavailable | Indeterminate/possibly-created with operation/request evidence and reconciliation requirement. Preserve returned URL as evidence even alongside failure, without treating arbitrary output as trusted identity. |

GitHub documents that private-resource authentication failures may appear as 404 and rate limiting as 403/429, with retry metadata; no status-only inference can collapse them safely. [REST API troubleshooting](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api). The current CommandError preserves wrapped process cause and raw diagnostic output; it does not provide normalized HTTP categories or retry headers. A new transport/result abstraction may be needed, but it belongs within GitHub and its Application port, not a new product layer.

Create intent should carry explicit base/head scopes and branches, title/body/draft, compatible maintainer-modification policy and any expected head Revision justified by the use case. Application revalidates local/upstream intent through Git and remote existence through GitHub before submission. Missing/unpushed remote head must produce an actionable refusal; pushing remains a separate authorized Application/Git action. UI modal state is not an adapter precondition token.

The create API takes mutable head/base refs, not an atomic expected-head-OID condition. Pre-read then create is not a transaction against remote branch movement. Where exact head intent applies, verify before submission and inspect resulting PR facts; a mismatch after creation is a published-but-mismatched outcome requiring reconciliation, never a pretend rollback or automatic delete/close. REFDES must state this check-to-use limit without silently following changed refs. This is the remote counterpart of the accepted mutation-effect-state rules.

For uncertain creation, Application retains one terminal operation outcome and reconciles by exact base repository, qualified head repository/branch and base, with expected revision/created identity evidence where available. Query existing candidates under bounded completeness rules; an incomplete list cannot prove no PR was created. CLI's existing-PR check is helpful but insufficient. Retry only when its permitted effect is established; do not blindly resubmit or auto-adopt an unrelated preexisting PR. No server exactly-once guarantee is asserted.
