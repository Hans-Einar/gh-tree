## Review purpose and boundary

This review examines the horizontal Application responsibility deeply enough to define the required orchestration, port, operation, event, cancellation, read-model and confirmation semantics for the later Refactor Design and Boundary Contract stage.

The product evidence is frozen at exactly `f626077ca0e59fbe9ede7ba1116982bb94b2eb6b`. Governance, architecture and review commits after that SHA are process/design authority only and are not treated as product changes.

This is review only. It does not implement fixes, move files, freeze Boundary Contracts or authorize refactor implementation.

The accepted Runtime and TUI State reviews are treated as hard boundary inputs:

- Runtime owns whole process-tree/session resources and one collision-free Runtime session registry.
- Runtime exposes explicit capabilities and truthful lifecycle facts, with correlated exactly-once lifecycle events.
- Application owns product-operation sequencing, cancellation policy and operation correlation above Runtime.
- TUI State owns deterministic ephemeral interaction intent and emits declarative Application commands/effects.
- Application events/results may not own or overwrite TUI focus/navigation/modal selection.
- Concrete adapter DTOs do not cross into TUI State.
- confirmation state in TUI must be bound to exact Application operation/target identity.

The review therefore challenges current `app.Service` not only for cohesion but for whether it can satisfy those already-accepted boundaries.

## Layer responsibility

### Application must own authoritatively

Application should authoritatively own **vertical product use-case orchestration and operation lifecycle**, including:

1. accepted commands/queries and their semantic validation;
2. allocation and tracking of Application `OperationID` values;
3. operation state (`accepted`, `running`, `waiting-confirmation`, `cancelling`, terminal result);
4. exactly-once terminal Application result for every accepted operation;
5. cancellation and safe supersession policy for operations;
6. sequencing calls across Application-owned ports;
7. safe confirmation protocols for destructive or state-sensitive operations;
8. active-worktree session context and coordination of its durable preference;
9. cross-source reconciliation/read models such as local/upstream/GitHub branch relationship;
10. cross-source joins such as Git graph facts + GitHub PR facts + worktree facts;
11. normalization of adapter-specific errors into use-case errors/results where needed;
12. normalization of Runtime lifecycle facts/events into Application session projections;
13. stable Application API DTOs/read models that TUI State can consume without importing concrete adapters;
14. request correlation metadata needed to echo TUI request generation/intent tokens without interpreting focus;
15. product-level shutdown orchestration when Composition requests an orderly application shutdown.

Application is where a vertical Slice becomes one coherent operation. It is not merely a namespace for adapter methods.

### Application must NOT own

Application must not own:

- Bubble Tea key routing, focus, pane/subpane selection, console-tab selection or modal rendering;
- Lip Gloss styles, terminal layout, viewport geometry or animation frames;
- Git command execution, local ref mutation mechanics, worktree filesystem mechanics or stash implementation;
- GitHub CLI/API transport implementation;
- OS process handles, PIDs/process groups, Job Objects, PTY/ConPTY handles or Runtime resource cleanup implementation;
- launch manifest/provider parsing implementation;
- filesystem persistence implementation or path policy;
- adapter-private DTOs as its public API;
- provider-string or concrete-manager routing decisions;
- automatic cancellation of irreversible/destructive mutations merely because a TUI request became visually stale;
- durable storage of UI-only focus/selection state unless a separate product requirement explicitly makes such state persistent.

## Challenge of Broad Review findings

### BR21-H05 — confirmed and strengthened

The Broad Review states that `app.Service` is largely a concrete-adapter facade. Deep inspection confirms this and reveals a stronger structural problem: **the current Application package has no Application-owned port model, operation model or stable public DTO model at all.**

`Service` stores concrete pointers to `github.Client`, `worktree.Manager`, `graph.Reader`, `diff.Reader`, `launch.SessionManager`, `terminal.Manager` and a concrete `launch.Registry`. Its public methods accept and return `github`, `worktree`, `graph`, `diff` and `launch` types. This makes the package depend on every concrete implementation it is supposed to orchestrate.

A few methods do contain meaningful orchestration (`Load`, `LoadGraph`, PR worktree preparation, launch start, PR diff, terminal start), but the majority are direct pass-throughs. Renaming the package or moving `Service` wholesale would preserve the defect.

### BR21-H03 — confirmed and strengthened

The v0.3.14 deploy workflow is split across TUI, `app.Service` and `worktree.Manager`. `V314Model.executeDeploy314` decides whether to stash, creates the stash, then chooses branch/PR/commit deployment through three backend generations. Application exposes primitives such as `StashPush`, `DeployBranchDetached`, `DeployPRDetached` and `CheckoutWorktree` but does not own the whole operation.

The deeper defect is not only misplaced sequencing. There is no stable confirmation identity or precondition version. A dirty-status observation is captured, the user confirms, and later mutation proceeds without an Application-owned token proving that the confirmation still refers to the same active worktree/target/status generation.

Deploy therefore needs one Application use case with a confirmation protocol, not merely a shorter set of facade methods.

### BR21-M02 — confirmed

The current code exposes at least three different branch-tip observations:

- local worktree/branch HEAD from Git;
- upstream/remote-tracking state and ahead/behind from local Git observations;
- GitHub branch SHA from the GitHub adapter.

Application has no canonical branch relationship read model and no freshness/reconciliation policy. `Snapshot` simply places GitHub branches next to worktrees. Graph additionally marks local/remote refs, but those refs are explicitly only local observations and may be stale.

Application should reconcile these facts without pretending they were observed at the same freshness boundary.

### BR21-M03 — confirmed and refined

`app.Service.LoadGraph` already performs part of the correct Application job by loading PRs/worktrees before calling `graph.Reader.Load`. However, `graph.Reader.Load` itself accepts concrete GitHub PR/worktree DTOs and performs the cross-source annotation join. `Service.GraphHistory` then converts those graph objects into `worktree.Commit` while embedding human-oriented decoration strings into subject/message text.

The correct split is:

- Git port returns pure local graph/ref/HEAD facts;
- GitHub port returns remote PR/branch facts;
- Application joins them into a semantic graph read model;
- TUI View formats labels/messages.

### BR21-M04 / BR21-M08 — confirmed and strengthened

`cmd/gh-tree/main.go` passes `StateStore.SetLastFolder` and `SetLastWorktree` callbacks directly into TUI. TUI changes `activeWorktree` and calls persistence itself.

The stronger Application requirement is that active worktree is a product/session concept, not just a persisted path. Application must own the current active-worktree context, validate/reconcile it against current Git worktree facts, update Persistence through a port, and emit one normalized result/read-model update. The TUI may select a candidate but must not directly make durable product truth.

### BR21-M05 — confirmed with accepted Runtime constraints

`Service.StopAllConsoles` serially calls two concrete managers and returns only the first error; Composition discards even that error in a defer. This cannot satisfy the accepted Runtime requirement that successful shutdown proves all Runtime-owned resources are terminal and cleaned and that failures report residual sessions/resources.

Application should request one Runtime shutdown operation and report its aggregate terminal result upward; Runtime remains the lifecycle/resource authority.

### BR21-M07 — confirmed

`worktree` owns Git primitives plus higher-level deployment/preparation structures, while `app.Service` accepts/returns those concrete types directly. The Application review cannot fully decide the Git/Domain split before their focused reviews, but it confirms that adapter structs cannot remain the cross-layer API.

## State authority

### Application-authoritative state

Application needs authoritative ephemeral product-operation/session context distinct from adapter truth and TUI interaction state.

| State | Application authority | Notes |
|---|---|---|
| operation registry | yes | accepted operation ID, kind, target identity, lifecycle, cancel/supersession state, terminal result |
| active worktree session context | yes | semantic active worktree ID/path as currently selected product target; reconciled against Git facts |
| canonical branch relationship projection | yes, derived | derived from Git + GitHub observations, including freshness/unknown states |

| Git ref/worktree/stash truth | no | Git adapter only, observed through port |
| GitHub remote truth | no | GitHub adapter only, observed through port |
| persisted bytes/files | no | Persistence only |

### Operation truth versus UI request relevance

Two different notions must remain separate:

1. **Operation truth** — Application knows whether a command is accepted/running/cancelling/completed/failed/superseded.
2. **UI relevance** — TUI State knows whether the user still wants a completion to alter a projection/modal/auto-follow decision.

Application must not own focus. TUI may mark an intent token/request generation superseded. Application may use an **opaque supersession scope/correlation value** to cancel or supersede operations only where the use-case contract says doing so is safe.

A stale UI result does not imply the underlying mutation never happened.

Example: a read-only graph query can normally be cancelled/superseded when a newer graph generation exists. A stash drop or Git commit already executing must not be silently abandoned or forgotten merely because the user navigated elsewhere. It still receives exactly one terminal Application result; TUI may choose not to auto-open/auto-focus anything in response.

## Operation, cancellation and event model

### OperationID

Application should allocate a collision-free `OperationID` for every accepted async command/query. Exact representation (monotonic integer, UUID-like value) is design-level, but identity must be stable during one process lifetime and test-injectable or deterministic enough for unit tests.

An operation record conceptually contains:

- `OperationID`;
- operation kind;
- immutable semantic target identity;
- caller correlation metadata;
- start/accept time if needed for diagnostics;
- cancellation handle derived from Application/root context;
- lifecycle state;
- optional confirmation token/precondition;
- optional Runtime `SessionID` correlation;
- exactly one terminal result.

### Exactly-once result rule

For every accepted OperationID:

- zero or more progress/domain events may be emitted;
- exactly one terminal Application result must be emitted;
- terminal states include success, failed, cancelled, superseded where safe/meaningful;
- late adapter/Runtime callbacks after terminal completion are ignored for operation mutation but may be logged/diagnosed according to design;
- duplicate terminal Runtime events must not produce duplicate Application terminal results.

### Cancellation

TUI State must not create `context.Background()` lifetimes for product operations.

Application should derive each operation context from an Application/root lifetime supplied by Composition. `CancelOperation(OperationID)` records cancellation intent and invokes cancellation through the relevant port/context.

Cancellation semantics are use-case-specific:

- read-only queries: normally cancellable and supersedable;
- pending operations before mutation: cancellable if no irreversible step began;
- Git mutation in progress: port must define cancellation safety; cancellation result must reflect whether mutation may have completed/partially completed;
- Runtime Start: cancellation must obey Runtime failed-start/cleanup guarantees;
- Runtime Stop/Shutdown: cancellation must not mean abandoning owned resources; accepted Runtime semantics take precedence;
- confirmation waiting: cancellation safely terminates the pending operation/confirmation token.

### Supersession

Application owns whether an operation *can safely be superseded*, but TUI owns whether a result is still relevant to user interaction.

Recommended rule:

> A newer request may supersede an older operation only within an explicit supersession scope defined by the use case. Supersession may cancel work where safe, but it never rewrites TUI focus and never erases the need for a terminal result from a mutation that may already have side effects.

For example:

- navigator refresh generation 8 can supersede generation 7;
- branch-history request for a newly selected branch can supersede an older read request;
- a new deploy request does not silently supersede an already-mutating deploy;
- user Alt+N after starting a console supersedes the TUI auto-follow intent, not the Runtime start operation itself.

### Runtime event correlation

Runtime should receive Application correlation when a lifecycle call is initiated and echo it with Runtime `SessionID`/lifecycle event identity.

Application then maps Runtime facts to stable session projections such as:

- SessionID;
- lifecycle state;
- capabilities;
- invocation/display identity supplied from Domain/Application launch definition;
- exit result;
- output sequence/availability metadata;
- residual cleanup state when failure occurs.

Application must not expose Runtime concrete manager/provider strings as behavioral routing instructions.

## Confirmation protocol

Current boolean/string modal flags are not sufficient for destructive/state-sensitive operations.

A confirmation-required use case should conceptually work as follows:

1. TUI sends command intent, e.g. `PrepareDeploy(target, activeWorktree)`.
2. Application allocates OperationID and queries authoritative current preconditions through ports.
3. If no confirmation is needed, Application may continue according to command contract.
4. If confirmation is needed, Application emits `ConfirmationRequired` containing:
   - OperationID;
   - opaque ConfirmationID/token;
   - exact semantic target identity;
   - exact active-worktree identity;
   - precondition/version/fingerprint sufficient to detect stale confirmation;
   - allowed choices (`stash-and-deploy`, cancel, etc.);
   - semantic warning data, not rendered prose only.
5. TUI State displays a modal bound to that exact OperationID/ConfirmationID.
6. User confirmation sends `ConfirmOperation{OperationID, ConfirmationID, choice}`.
7. Application revalidates required preconditions. If materially changed, it rejects with `ConfirmationStale` and does not perform the destructive step until a new confirmation is obtained.
8. Completion closes only the TUI modal bound to the matching operation; TUI decides that state transition.

The same pattern may apply to destructive stash drop/restore/checkout where the Domain/Git safety contract requires it. Not every simple command needs a two-stage protocol.

## Canonical read-model and reconciliation responsibilities

### Branch relationship

Application should produce one canonical branch relationship read model rather than letting TUI compare unrelated fields.

Conceptually it needs to distinguish:

- local branch name/tip if present;
- configured upstream ref if present;
- locally observed upstream/remote-tracking tip;
- ahead/behind/diverged relation based on a known Git comparison point;
- GitHub branch tip if present;
- whether GitHub/local upstream observations agree;
- freshness source: locally cached remote-tracking observation versus GitHub observation versus post-fetch local observation;
- unknown/not-observed states explicitly, rather than zero-value SHA inference;
- detached worktree state;
- unpushed local branch state;
- remote-only branch state.

The Git review must define exact local primitives and freshness guarantees; GitHub review must define remote facts. Application owns the reconciliation policy/read model.

### Graph

Git port should return graph commits/refs/HEAD facts only. Application joins:

- PR annotations from GitHubPort;
- worktree annotations from GitPort facts;
- canonical branch/remote relation where required;
- pagination/freshness metadata.

The result should remain semantic. TUI View decides how `[L:]`, `[R:]`, PR arrows and prose are displayed.

### Repository overview/navigator

`Service.Load` is the clearest existing genuine Application query. Target form should:

- load GitHub PR/branch facts and local Git/worktree facts through ports;
- preserve per-source freshness/error semantics;
- return a stable Application read model;
- avoid leaking `github.PullRequest`, `github.Branch`, `worktree.Info` directly;
- define whether partial data is allowed if one source fails.

### Active worktree

Application should maintain one active-worktree session context keyed by semantic worktree identity/path.

On activation:

1. validate candidate against current Git worktree facts;
2. update Application session context;
3. persist through PersistencePort;
4. if persistence fails, follow an explicit atomicity policy (recommended: do not report durable activation success ambiguously; exact rollback/availability policy belongs in Refactor Design/BC);
5. emit updated active-worktree projection;
6. let TUI trigger/display related queries without directly persisting.

Startup should load the persisted preference through PersistencePort, reconcile it against current Git worktrees, and deterministically choose fallback behavior if missing/stale.

## Error and safety semantics

### Typed use-case errors

Current raw strings such as “worktree operations are unavailable” and manager membership checks are not enough for deterministic orchestration. Application should be able to distinguish at least conceptually:

- capability unavailable/not configured;
- target not found/stale;
- precondition failed/dirty;
- confirmation required;
- confirmation stale;
- unsupported session capability;
- operation cancelled;
- operation superseded;
- adapter transport failure;
- mutation failed with state unknown/partial;
- Runtime cleanup residual resources;
- persistence failed.

Exact error types belong to Refactor Design/BCs.

### Partial read failures

`Service.Load` currently discards all results if any concurrent source returns an error. Refactor Design should explicitly decide which read models allow partial availability. For example, GitHub unavailable while local Git facts remain usable may be representable as a partial repository overview with source error/freshness metadata instead of a total blank failure.

This is a product policy decision for Application, not an adapter behavior accident.

### Mutations

For Git/persistence/runtime mutations, Application must never report success solely because an initiating call returned before authoritative completion semantics are satisfied.

Where a port cannot guarantee rollback after cancellation/failure, terminal result must communicate state uncertainty and trigger an explicit refresh/reconciliation path.

## Lifecycle / concurrency

Application itself should not own OS resources, but it does own lifecycle of logical operations and subscriptions/correlation.

Required concurrency invariants:

1. OperationID allocation is race-safe and collision-free.
2. An operation transitions to a terminal Application state once only.
3. Cancellation is idempotent.
4. progress after terminal completion cannot reopen an operation.
5. duplicate/late Runtime events cannot duplicate terminal results.
6. supersession affects only declared scopes and never silently discards mutating operation outcomes.
7. confirmation token may be consumed once only.
8. confirmation is rejected if target/precondition generation no longer matches.
9. active-worktree changes are serialized or otherwise versioned so older persistence/query completions cannot overwrite a newer activation.
10. read-query generations are independently testable; stale result delivery is either suppressed by Application where appropriate or safely rejected by TUI correlation.
11. shutdown prevents new Runtime-start operations once shutdown acceptance has begun, unless the final design deliberately specifies another policy.
12. Application/root context is owned by Composition and cancelled during shutdown; child operation contexts derive from it.

## Disposition

`ACCEPTED — FOCUSED APPLICATION REVIEW COMPLETE / REFACTOR NOT AUTHORIZED`

The target Application layer is confirmed as necessary, but the existing `app.Service` is not a viable structure to preserve wholesale. It contains a small number of genuine orchestration paths surrounded by a much larger concrete-adapter facade. The target must instead be built around coherent use cases, Application-owned ports, stable read models, an explicit OperationID/cancellation/exactly-once-result model, confirmation/precondition identity, and canonical cross-source reconciliation.

- TUI State owns user interaction intent and decides focus/modal/tab behavior;
- Application owns product operation lifecycle, safe supersession policy, use-case sequencing and cross-source read models;
- Runtime owns session/process-tree resource truth and echoes lifecycle correlation;
