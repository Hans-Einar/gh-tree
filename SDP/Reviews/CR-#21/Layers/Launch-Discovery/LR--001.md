## Layer responsibility

Launch Discovery should own passive provider detection, reading provider manifests, parsing supported launch definitions, identifying project scope, validating and resolving selected launch intent, and producing normalized immutable definitions and invocation data. Its target is internal/launchdiscovery/.

It must not execute provider tools during discovery, start/stop sessions, allocate SessionID or OperationID, access concrete Runtime/Persistence/Git adapters, select the active worktree, persist user intent, own a default-selection workflow, or decide TUI focus/modal state.

Application validates active-worktree context through Git, coordinates Persistence load/save, asks Launch Discovery to interpret or resolve launch intent, and sends the resolved execution specification to Runtime. Runtime alone owns execution, executable lookup/platform launch mechanics, sessions, cancellation of established processes, and shutdown.

Only LaunchPointID is currently justified in Domain. A launch definition is an observation of mutable project/configuration files, and executable/argv/cwd are execution-boundary data. This review finds no additional pure Domain launch definition necessary. Keep normalized definitions and invocation specifications in Application-owned port/API types, with provider/parser/build records private to Launch Discovery. Domain remains the accepted small value layer.

## Current behavior and retained strengths

Registry discovers only directories with actual provider manifests. A root package-lock.json alone creates no npm launch. Nested manifests are supported, with slash-separated relative project directories; supported depth is root plus at most five path components. Names are case-insensitively excluded for .git, .gh-tree, node_modules, vendor, dist, build, out, target, .next and .cache (E1:43-105,151-157).

The npm family requires package.json; its scripts are sorted and each exact key is stored in Script. Colon splitting is for the display Path only. For ordinary keys such as dev:wan, Build produces one argument after run, not multiple commands (E2:20-62; E5). Package-manager precedence is project-local pnpm-lock.yaml, then yarn.lock, then npm. package-lock.json is not required for npm; ancestor locks/workspace metadata and packageManager are not consulted. pnpm/yarn remain implementations of the npm script provider, not Runtime kinds.

Make uses a passive heuristic parser for simple literal targets, sorts discovered names, and preserves the selected target order in one native argv. It does not execute make to enumerate targets. This is valuable because even evaluating a build tool for discovery can execute project-defined behavior. Ordered arguments do not promise a new gh-tree scheduler or stronger recipe ordering than the selected native Make implementation/environment (E3; E5).

Configuration already distinguishes missing file from read/JSON errors, validates that the default alias exists, rejects an empty alias, npm target stacks, Make scripts, empty Make stacks, unknown providers, and lexical path escape. Targets are copied when building invocations and mapping saved records. These safeguards must survive migration (E4:30-118,127-155).

### Safety meaning and evidence limits

LD36-H01 is a real containment failure in the reviewed validation path, not a claim that every directory symlink is recursively scanned. Build accepts configured candidates independently of traversal. Link/reparse behavior differs by platform; a lexical path policy or a library call without platform evidence cannot establish the README guarantee. This is cwd scope protection, not a sandbox against a user-selected project's own scripts.

LD36-H02 can execute a target in the wrong project, where clean/install/deploy-like names may have materially different effects. The code path and missing Enter/save guard establish the risk; the report did not execute such a target. Existing TestV039MakeStackDoesNotCrossProjectRoots calls the helper directly and therefore does not prove the end-to-end picker transition.

GNU Make documents its default file search as GNUmakefile, makefile, Makefile, and that a leading-hyphen goal is interpreted as an option. Therefore both differing-manifest and option-shaped-target risks are grounded in the native semantics, not shell interpolation. [GNU Make manual, Makefile names](https://www.gnu.org/software/make/manual/make.html#Makefile-Names), [GNU Make manual, goals](https://www.gnu.org/software/make/manual/html_node/Goals.html).

An arbitrary c.Command is currently an executable override, not a shell-concatenated command. Saving a discovered candidate freezes the chosen manager name in command; manually authored configurations may also contain it. No automatic launch or remote exploit is asserted. The design must preserve or explicitly migrate accepted override behavior and validate it consistently; it must not quietly reinterpret command as shell source or remove existing settings.

## Repository-relative cwd and source resolution

The configured dir is relative to the selected worktree root, not the invocation process cwd, original checkout, repository administrative directory or user config directory. Empty dir and dot mean that worktree's root. Nested manifest cwd is its own project directory. Preserve exact directory names and use a stable persisted slash representation without assuming Windows and Unix path grammars are interchangeable.

The later contract must cover absolute paths, traversal, Windows drive-relative/rooted/UNC/device forms, separators, case and volume identity, nonexistent/non-directory targets, linked roots, nested symlinks/junctions/reparse points, and link replacement between resolution and Start. Root identity should be canonicalized by the owning Git/Composition boundary; Discovery must validate selected project containment against that concrete root. Runtime must not silently start in another cwd if it has disappeared or changed.

Recommended compatibility policy is to retain ordinary in-worktree project paths and reject physical escapes with an explicit path result. If REFDES permits some in-root links, it must prove the resolved destination remains within scope on each supported platform; otherwise reject such paths explicitly. This is not a new filesystem layer or permission prompt. The precise platform implementation and residual check-to-use guarantees require design/verification; this review does not pretend passive filesystem reads are an atomic snapshot.

Selection revalidation should bind ID, WorktreeID/project root, exact member identity/order, effective executable policy and relevant manifest/config version. At resolution, a missing or materially changed selection yields a typed stale/missing result, not silent substitution of another script/project/provider. Application refreshes through an operation correlated to current TUI intent. This cannot guarantee that every dependency or script body remains unchanged after a process starts; define the versioned inputs and limit that promise explicitly.

## Configuration versus Persistence

The authoritative split is:

- Launch Discovery reads package.json/lockfiles/Makefiles as provider source facts and semantically validates/resolves provider launch intent.
- Persistence reads and writes gh-tree-owned configuration, including worktree-local .gh-tree/run.json. It owns location, JSON/schema decoding, missing/corrupt distinction, storage generation and write mechanics.
- Application coordinates loading those records, validation through Discovery, user save/default decisions, and Runtime start. Adapters never call each other.

RunConfig/LaunchPoint JSON structs must not move wholesale into Domain or become public concrete Persistence DTOs. Persistence maps the legacy format into Application-owned settings/intent data; Discovery interprets the semantic provider options behind its port. The final tagged intent versus versioned opaque-options representation belongs in REFDES, but it must preserve existing provider, dir, script, targets, command, aliases and default losslessly and avoid leaking concrete Candidate/Provider types.

The file is committable project launch intent, resolved per active worktree; it is not the per-user active-worktree preference or ephemeral launch cursor/console tab. Saving a new automatic alias must detect collisions; an intentional update of an existing named intent is a separate explicit semantic action. First save currently becomes default even when makeDefault is false and no default exists (E4:152-153); preserve or deliberately document that policy. Default execution must not invent a fallback when configuration is missing, invalid or stale.

Persistence's next review must settle atomic replacement and crash/durability promises, protection of .gh-tree and run.json link targets, concurrent save/version conflicts, corrupt-file recovery, unknown-field/schema migration and old aliases. Direct rewrite currently drops unknown JSON fields; introducing a schema/version must not silently erase forward or user-authored configuration. There is no permission here to rewrite users' files or change durable scope.

## Lifecycle / concurrency

Discovery owns only temporary filesystem handles and parse work. Make closes its input file with defer; npm reads data into memory. No Discovery operation has an established session whose lifecycle survives the request.

Accept context on Discover/Resolve/Validate where reads occur; observe cancellation between directory entries, providers and bounded reads. Local filesystem calls may not be immediately interruptible, so cancellation latency/limits must be stated without claiming instantaneous cancellation. Define maximum inspected directories/files, manifest bytes, candidates and Make scanner token size; current depth limit alone does not bound tree breadth or package.json size.

Registry/provider construction should be immutable, uniquely named, deterministic and race-safe for concurrent requests. Results must use a total stable identity order, not display strings as an implicit authority. Discovery emits no TUI events; Application wraps its result with OperationID and query/source generation. Query cancellation can stop further observation, but late results still require generation rejection.

Discovery caches, if introduced, need explicit source version/invalidation. Current TUI launchLoadedPath is inadequate: same-path refresh races cannot be distinguished, manifest changes do not change the key, and an error marks the path loaded before returning (E8:39-48). Move cache policy to the owning observation/use-case boundary; leave only current projection/selection correlation in TUI State.

## Error and safety semantics

At minimum distinguish missing worktree/project, no supported manifest, no launch points, invalid manifest/config, unsupported provider/intent, invalid/escaped cwd, missing/stale selected member, ambiguous/conflicting source/manager, incompatible selection group, limit reached, cancelled, and filesystem failure. Do not collapse access-denied into absent via bool Detect.

For partial discovery, recommend returning complete per-project/provider results with deterministic diagnostics and completeness metadata. Application decides whether a partial list is usable; it must not present a truncated/failed scan as an empty exhaustive list. Root-scope failure/cancellation must be explicit. Existing all-or-nothing behavior is observed, not permission to change public availability policy before design acceptance.

No configuration save occurs during Discover/Resolve. Invalid or stale intent prevents Runtime Start. Errors from Persistence prevent a false durable-save success. No fallback silently changes the selected exact script, Make project, executable policy or default alias.
