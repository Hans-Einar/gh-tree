## Review purpose and boundary

This review defines the smallest stable semantic model needed by the accepted target architecture. It deliberately rejects the idea that every cross-package struct should move into Domain. A type belongs here only when its identity or invariant remains meaningful independent of Git command implementation, GitHub transport, Runtime process mechanics, Launch Discovery provider details, Persistence format, Application orchestration and TUI presentation.

The product evidence is frozen at exactly `f626077ca0e59fbe9ede7ba1116982bb94b2eb6b`. Governance and review commits after that SHA are authority for process/design only and are not treated as product changes.

This is review only. No product code is modified, no file move is performed, no Boundary Contract is frozen and no implementation branch is authorized.

## Layer responsibility

### Domain must own

Domain should own only small, immutable semantic identities and invariants that several layers need to agree on:

1. repository-scoped identity vocabulary;
2. full Git object identity (`OID`) and exact immutable commit `Revision` semantics;
3. logical branch identity distinct from a Git refspec or remote-tracking observation;
4. PR identity distinct from mutable PR head/base/status facts;
5. worktree identity and the semantic attached-vs-detached HEAD shape;
6. stable stash identity based on Git object identity, not reflog position;
7. stable launch-point identity where provider implementation is irrelevant;
8. one opaque Runtime `SessionID` value shared upward;
9. typed operation-target identities that preserve exact selected revision authority;
10. constructors/equality rules that make empty, malformed or contradictory identities unrepresentable where practical.

Domain values should be immutable, comparable where practical and contain no I/O, clocks, goroutines, caches, mutable lifecycle state or adapter handles.

### Domain must explicitly NOT own

Domain must not own:

- Git command execution, refspec construction, remote names, fetch generations or remote-tracking freshness;
- configured-upstream resolution, ahead/behind observations, `gone/unresolved` state or canonical local/upstream/GitHub reconciliation;
- worktree dirty/staged/untracked/conflicted counts, lock/prunable facts, `Primary`/`Current` observations or status fingerprints;
- GitHub transport DTOs, PR title/state/draft timestamps or GitHub observation freshness;
- Application `OperationID`, operation lifecycle, cancellation/supersession policy, confirmation tokens or cross-source read models;
- Runtime lifecycle state, PID/process tree, capabilities, output, exit state, PTY/ConPTY facts or resource cleanup;
- Launch Discovery provider names, scripts, Make targets, npm details, command building or provider-specific candidates;
- normalized Runtime start specifications unless the later Launch Discovery review proves a genuinely provider-independent semantic definition that needs Domain ownership;
- graph annotations, navigator/read-model snapshots, diff payloads, human labels or presentation strings;
- persistence schemas, JSON tags, filesystem canonicalization or repository path policy;
- TUI focus, selection, modal, view or intent state.

The Domain layer is therefore a value/invariant layer, not a shared DTO package.

## Challenge of accepted review candidates

The accepted Application review intentionally left several candidates for Domain. This review narrows them:

- **Repository identity:** Domain-owned, but as an opaque canonical product scope, not a GitHub `owner/name` parser or filesystem path policy.
- **Commit ID/SHA:** Domain-owned as a generic full object ID and exact `Revision` value.
- **Branch identity:** Domain-owned as repository + logical branch name. Full Git refnames/refspecs and remote-tracking refs remain Git facts.
- **PR identity:** Domain-owned as repository + positive PR number. PR title/state/draft/head/base are remote facts/read models.
- **Worktree identity/basic head state:** Domain-owned only for identity and attached-vs-detached semantic shape. Status and availability remain Git/Application facts.
- **Stash identity:** Domain-owned as repository + stash commit OID. Positional reflog reference is never authoritative identity.
- **LaunchPoint:** only stable LaunchPoint identity is proven ready for Domain now. Provider/candidate/invocation details remain deferred to the Launch Discovery review rather than being prematurely promoted.
- **Runtime SessionID:** Domain-owned shared scalar vocabulary; lifecycle/capability facts remain Runtime/Application.
- **Branch relationship enums/value objects:** the full canonical `BranchRelationship` remains Application-owned. Freshness and observation states remain Git/GitHub/Application. No Domain branch-reconciliation aggregate is justified.
- **Safe-operation classifications:** no generic safety enum is justified yet. Exact target identities belong Domain; precondition fingerprints, confirmation protocol and mutation effect-state belong Git/Application.

## Candidate Domain value objects and invariants

Names below are design candidates for Refactor Design. The semantic requirements are the review conclusion; exact Go spelling may be refined later without weakening the invariants.

### `RepositoryID`

Conceptual shape: an opaque, comparable canonical token identifying the selected repository scope.

Required invariants:

- non-zero/non-empty;
- equality is exact canonical-token equality;
- source-specific GitHub URL/`owner/name`, local root path, remote URL and filesystem canonicalization are **not** parsed inside Domain;
- Composition/Application/adapters derive the canonical token and map their source-specific locators to it;
- repository-scoped IDs below include RepositoryID so semantically similar names from two repositories cannot be mixed.

The precise derivation scheme for the canonical repository token is a Refactor Design/Composition/Persistence question, not a Domain filesystem/network concern.

### `ObjectFormat`, `OID`, `Revision`

Domain should support Git SHA-1 and SHA-256 object IDs generically rather than encode a permanent 40-character assumption.

Conceptual representation:

```text
ObjectFormat = SHA1 | SHA256
OID          = { format, fixed immutable bytes }
Revision     = exact commit OID
```

Required `OID` parsing/normalization:

- accept only **full** object IDs: exactly 40 hex digits (SHA-1) or 64 hex digits (SHA-256);
- accept upper/lowercase hex input but normalize string output/equality to lowercase canonical hex;
- reject abbreviations, `0x` prefixes, whitespace-containing values, non-hex characters and zero/empty values used as sentinels;
- algorithm is derived from length or retained explicitly in the value; equality includes object format and bytes;
- callers cannot mutate backing bytes;
- `String()`/equivalent yields canonical full lowercase hex;
- arbitrary Git revision expressions (`HEAD~2`, `origin/main`, `refs/...`) are **not** `Revision`; they remain Git query/locator syntax.

`Revision` means an exact immutable commit identity. It may wrap/alias a validated OID constrained to commit use; operations that accept an exact selected commit should not accept a generic string.

### `BranchName` and `BranchID`

Conceptual shape:

```text
BranchName = non-empty logical branch name
BranchID   = { RepositoryID, BranchName }
```

Domain should not duplicate Git's complete `check-ref-format` implementation. Git remains authoritative for whether a name is usable as a concrete local ref. Domain should enforce only stable semantic invariants such as non-empty/non-NUL identity and leave Git-specific syntax validation at the Git boundary.

Full refnames (`refs/heads/...`), remote-tracking names (`refs/remotes/...`), managed PR refs and refspecs remain Git-owned facts/mechanics. No generic Domain `RefName` is required by current evidence.

### `PullRequestID`

Conceptual shape:

```text
PullRequestID = { RepositoryID, Number > 0 }
```

Only identity belongs here. Title, state, draft flag, base/head branch, head OID and `UpdatedAt` are GitHub observations/Application read-model facts.

An operation that means “the PR head I selected” must pair `PullRequestID` with an expected immutable `Revision`; PR number alone is mutable authority.

### `WorktreeID` and semantic `Head`

Conceptual Worktree identity:

```text
WorktreeID = { RepositoryID, opaque WorktreeKey }
```

`WorktreeKey` is a non-empty canonical key minted by the Git boundary from the registered worktree identity. Domain must not call `filepath.Abs`, resolve symlinks or decide platform case folding. The current product may initially derive the key from a canonical registered path, but that derivation remains outside Domain.

An established HEAD that resolves to a commit must be represented as a validated two-variant value:

```text
AttachedHead { BranchID, Revision }
DetachedHead { Revision }
```

or an equivalent closed representation with constructors that enforce:

- every established attached/detached head has an exact Revision;
- attached head requires a branch;
- detached head has no branch;
- “detached = true plus non-empty branch” and “attached plus empty branch” are impossible values.

This is not an exhaustive model of all observable Git HEAD states. A new repository
or orphan branch can have an **unborn HEAD**: a symbolic branch name without an
existing commit. This is distinct from malformed/unresolvable HEAD and must not
be mapped to detached HEAD. Baseline `worktree.go:parsePorcelain` retains raw non-empty HEAD
and branch fields, `ops.go:Status` consumes that inventory, and Composition has
no committed-HEAD admission gate. This is boundary evidence, not a claim that
every current operation supports unborn repositories.

Refactor Design must explicitly choose either a pure `UnbornHead{BranchID}`
variant with no Revision, or a typed Git/Application unsupported-state result
that leaves existing established-Head values unchanged. It must specify how
inventory/status and the TUI represent that observation. An unborn/null protocol
OID must never become a valid Domain OID/Revision, and exact-revision mutations
must refuse when there is no exact commit. This correction does not authorize
new unrelated unborn-repository features.

The following are **not** Domain Worktree state: path display string, Primary, Current, locked/prunable, dirty counts, upstream state, filesystem availability or active-worktree preference.

### `StashID`

Conceptual shape:

```text
StashID = { RepositoryID, OID }
```

The OID is the stash commit/object identity. `stash@{0}` / `stash@{n}` is a mutable reflog locator/display fact, never the authorization identity for a destructive action.

Required rule: if Git uses a positional reflog locator to execute a stash command, it must re-resolve that locator immediately before mutation and verify it equals the expected StashID OID. Mismatch means stale target/refusal, not “operate on whatever is now at that position”.

Subject, file count, managed metadata, origin path/branch/head and creation time remain Git/Application facts/read models unless later evidence proves a separate stable semantic requirement.

### `LaunchPointID`

Current evidence proves a need for a stable selection identity but does **not** prove that the entire `launch.Candidate` or `Invocation` is a Domain value.

Conceptual shape:

```text
LaunchPointID = { WorktreeID, opaque Key }
```

The Key is non-empty and provider-independent at the Application boundary. Launch Discovery is responsible for mapping npm/Make/config provider data to this identity and to normalized launch-definition/execution DTOs.

Provider, script, Make target, discovery path, command, args and cwd do not move wholesale to Domain. The next Launch Discovery review may prove a minimal immutable `LaunchPointDefinition` worth extracting; this review intentionally does not pre-empt that evidence.

### `SessionID`

Conceptual shape:

```text
SessionID = opaque uint64-like non-zero value
```

Required invariants from the accepted Runtime review:

- allocated only by one authoritative Runtime session registry;
- collision-free across all session kinds during one gh-tree process lifetime;
- zero is invalid/unassigned;
- never reused during that process lifetime;
- Restart creates a new SessionID;
- value contains no provider/kind routing information;
- TUI/Application compare/pass it but cannot manufacture behavioral meaning from its numeric value.

PID, lifecycle state, capability flags, invocation, output, exit result and cleanup state remain Runtime facts/Application SessionProjection fields.

### Application `OperationID` is not Domain

`OperationID` is intentionally **not** a Domain value object. It identifies Application execution/correlation lifetime, not a stable product entity. Application remains its allocator and authority as already accepted.

The same applies to ConfirmationID, request generation, user-intent token, fetch generation, status/precondition fingerprint and Runtime event sequence.

## Operation-safe semantic target identities

Domain should prefer small typed target values used by specific commands rather than a giant weakly-typed `Target{Kind string, ...}` union.

Conceptually required forms include:

```text
ExactRevisionTarget = { RepositoryID, Revision }
BranchRevisionTarget = { BranchID, ExpectedRevision }
PullRequestRevisionTarget = { PullRequestID, ExpectedHeadRevision }
WorktreeTarget = { WorktreeID }
WorktreeRevisionTarget = { WorktreeID, ExpectedHeadRevision }
StashTarget = { StashID }
LaunchTarget = { LaunchPointID }
SessionTarget = { SessionID }
```

Application may compose these with `OperationID`, ConfirmationID and Git-supplied precondition/fingerprint values. Those orchestration/precondition values do not become Domain merely because they travel alongside a Domain target.

A future command intentionally meaning “whatever is currently at branch X” must use a different Application command contract from `BranchRevisionTarget`; it must not silently drop `ExpectedRevision` from an exact user selection.

## Ref vs Revision Authority

This is a mandatory design principle carried forward from the accepted Git review and strengthened here into Domain semantics.

### Definitions

- **Revision**: an immutable exact commit OID selected or otherwise fixed by product intent.
- **Ref/Branch/PR locator**: a mutable name/number that may point to a different Revision later.
- **ExpectedRevision**: the immutable Revision that a mutable locator must resolve to for an operation to satisfy the user's exact selection.

### Authority rules

1. When user intent selects an exact commit OID, **Revision is authoritative**.
2. A branch name, PR number, refname or remote-tracking name associated with that selection is metadata/locator, not substitute authority.
3. Application must preserve the selected Revision in its typed command/target; it must not reduce the command to only a branch/ref/PR name.
4. Git may fetch/resolve a mutable locator as a mechanism, but before mutation it must verify that the resolved commit equals ExpectedRevision.
5. A mismatch is a stale/changed-target refusal requiring refresh/reconciliation. The operation must not silently follow the newer or older ref.
6. After mutation, Git must verify the resulting relevant HEAD/ref/object identity equals the authoritative Revision where the operation contract promises an exact revision.
7. Freshness metadata cannot replace exact OID verification. A fresh observation can still change after observation; expected-OID comparison is the stronger safety invariant.
8. The existing PR exact-ref flow (`PreparePullRequest`: fetch -> resolve -> compare selected SHA) is the correct pattern to generalize.
9. The current branch-deploy flow is the counterexample: selected GitHub SHA is lost, and existing local branch name can win. Target design must make that impossible at the type/API level.
10. An explicit “latest by mutable ref” operation is legitimate only as a different use case whose Application contract states its freshness/reconciliation policy and does not pretend to preserve an earlier exact revision selection.

This principle belongs in Refactor Design and later `BC--Application--Git.md`; this review does not freeze that BC.

## Branch relationship ownership

Domain should own only the stable identities required to express the endpoints of relationships: RepositoryID, BranchID and Revision.

The canonical branch relationship object remains Application-owned because it is a reconciliation product over observations such as:

- local branch tip;
- configured upstream ref;
- locally observed remote-tracking tip;
- ahead/behind/diverged result;
- GitHub branch tip;
- GitHub-vs-local agreement;
- `none/resolved/gone/unresolved` observation state;
- fetch generation/freshness;
- remote-only/unpushed classifications.

Git owns local observation/freshness facts; GitHub owns remote observations; Application reconciles them. Domain must not acquire timestamps, fetch IDs or “current remote” policy merely to make that read model reusable.

If a later design finds a pure mathematical relation between two already-known Revisions worth sharing, a tiny value may be extracted then. Current evidence does not require it.

## Lifecycle / concurrency

Domain should contain no resource lifecycle or concurrency machinery.

Required purity rules:

- no goroutines, mutexes, channels or context lifetimes;
- no global mutable registries/counters;
- SessionID allocation occurs in Runtime, not a Domain singleton;
- OperationID allocation occurs in Application;
- Repository/worktree canonicalization occurs at appropriate outer boundaries;
- values are safe to copy/compare without synchronization;
- constructors perform deterministic validation only.

This separation prevents Domain from becoming a hidden second authority for Runtime/Application state.

## Error and safety semantics

Domain constructor errors should be narrow validation failures: malformed/zero OID, invalid PR number, empty RepositoryID/WorktreeKey/LaunchPoint key, zero SessionID or contradictory Head construction.

Operational errors do not belong here:

- stale expected OID / ref changed -> Git typed result normalized by Application;
- stash locator no longer maps to expected StashID -> Git stale-target/precondition failure;
- worktree dirty/precondition changed -> Git fact/precondition failure + Application confirmation protocol;
- remote freshness unknown -> Git/GitHub/Application read model;
- session not found/stopping/failed -> Runtime/Application;
- operation cancelled/superseded/confirmation stale -> Application.

The key safety contribution of Domain is preventing authority from being represented ambiguously, not performing I/O-time revalidation itself.

## Incoming boundary changes required

### From Git

Git port facts should use Domain OID/Revision, RepositoryID, BranchID, WorktreeID and StashID where they express stable semantics. Git-private parsers may remain primitive/string based internally.

Git must not push remote-tracking freshness, status fingerprints, refspecs or arbitrary revision expressions into Domain. For exact target operations it must accept expected Domain Revision/StashID values and verify its mutable locators against them.

### From GitHub

GitHub adapter should map owner/name/transport DTOs to Application facts that carry Domain RepositoryID, PullRequestID, BranchID and Revision. Remote observation timestamps/state remain outside Domain.

### From Runtime

Runtime should allocate one Domain SessionID vocabulary and return it with Runtime lifecycle facts. Runtime remains owner of uniqueness and all resource/lifecycle semantics.

### From Launch Discovery

Launch Discovery should map provider-specific candidates to stable LaunchPointID values at its boundary. Whether any further normalized immutable launch definition deserves Domain ownership is intentionally deferred to the focused Launch Discovery review.

### From Persistence / Composition

They must agree on how source-specific repository/worktree locators map to canonical RepositoryID/WorktreeID tokens without moving filesystem/serialization policy into Domain.

## Outgoing boundary changes required

Domain should expose only pure values/constructors/equality and narrowly required semantic helpers.

Application APIs may embed Domain values in commands, read models and events. Adapters may use Domain values at port boundaries. TUI State may see Domain values through Application projections for stable selection/correlation.

Domain should expose **no adapter ports**, no repository service, no query API, no process/session manager, no serializer and no presentation formatter.

## Tests / observability gaps

Required future Domain tests:

### OID / Revision

- valid SHA-1 40-hex input;
- valid SHA-256 64-hex input;
- uppercase input normalizes to lowercase canonical output/equality;
- reject 39/41/63/65 length, abbreviations, whitespace, prefixes and non-hex;
- reject zero/unassigned sentinel representation;
- SHA-1 and SHA-256 values never compare equal;
- round-trip canonical string;
- Revision cannot be constructed from arbitrary ref expressions.

### Identity values

- RepositoryID non-empty/canonical equality;
- PR number must be positive and repository scope participates in equality;
- BranchID equality includes repository scope;
- WorktreeID equality includes repository scope + opaque key;
- StashID equality includes repository + OID;
- LaunchPointID equality includes worktree scope + key;
- SessionID zero invalid and equality is opaque numeric identity only.

### Head semantics

- AttachedHead requires BranchID + Revision;
- DetachedHead requires Revision and exposes no branch;
- contradictory attached/detached combinations cannot be constructed;
- detached HEAD does not compare/evaluate as “branch with empty name”.
- unborn/orphan HEAD follows the accepted explicit boundary policy; inventory
  cannot fabricate a nonzero commit, and exact-revision operations refuse safely;
- Git integration tests cover a newly initialized repository and an orphan branch
  observation, alongside established attached and detached HEAD cases.

### Target semantics

- BranchRevisionTarget and PullRequestRevisionTarget retain ExpectedRevision through copies/mapping;
- targets from different RepositoryID scopes are unequal even with same names/numbers;
- mutable locator metadata cannot replace/remove expected Revision in exact-target constructors.

### Stash safety boundary tests

Domain unit tests cover StashID equality; Git integration/contract tests must separately prove positional locator re-resolution and expected-OID refusal on shifted stash lists.

### Session boundary tests

Domain unit tests cover value invariants; Runtime contract tests prove one allocator, no reuse/collision and new ID on Restart.

### Purity/import tests

- `internal/domain` imports only standard library packages;
- no JSON/YAML/TOML persistence tags or serializer dependencies are required on Domain values;
- no `context`, filesystem, network, process, Bubble Tea/Lip Gloss or adapter package dependencies;
- deterministic unit tests, no environment or Git/GitHub binaries.

## Unresolved questions intentionally deferred

1. **RepositoryID derivation:** exact canonical token derivation across GitHub locator/local repository/persistence belongs to Refactor Design plus later Persistence/Composition reviews. Domain only requires opaque stable equality and repository scoping.
2. **WorktreeKey derivation:** current path-based identity is sufficient evidence for an opaque key, but whether target design should use canonical path, Git worktree administrative ID or another stable key belongs to Git/Persistence/Refactor Design. Domain must not perform path canonicalization.
3. **LaunchPoint definition:** only LaunchPointID is proven stable now. The next Launch Discovery review must determine whether a normalized immutable definition beyond identity is genuinely provider-independent enough for Domain or should remain an Application/port DTO.
4. **OID all-zero representation:** product semantic object identity should treat zero as invalid/unassigned. If a future Git plumbing port needs protocol-level null OIDs, it should use a Git-specific optional/null representation rather than weakening Domain Revision.
5. **Serialization:** Persistence may need stable textual forms, but serializer schema/versioning should map through Persistence rather than adding storage tags/format authority to Domain.
6. **Unborn HEAD:** choose a pure no-Revision variant or an explicit typed
   unsupported-state mapping in Refactor Design, including inventory/status/TUI
   behavior. Established attached/detached values keep their nonzero exact
   Revision invariant; no protocol null OID is admitted into Domain.

These do not block the Domain ownership conclusion and should not be guessed into implementation before Refactor Design/later focused reviews.
